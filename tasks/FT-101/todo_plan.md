# FT-101 — План разработки

**Ограничение максимальной скидки в соглашении с клиентом**

Основание: [architecture.md](architecture.md)
Дата: 2026-08-20

---

## Порядок этапов

Этапы 0–2 дают заказчику работающее ограничение скидок **без единой строки кода**.
Этап 3 добавляет защиту нижнего порога цены — это уже доработка.

Если сроки спринта поджимают, режем по границе этапа 2: контур 1 самодостаточен
и закрывает первую из двух названных заказчиком болей.

---

## Этап 0. Разведка на боевых данных (блокирующий)

Без этого этапа остальные могут оказаться бессмысленными — см. Риск 1 в architecture.md.

- [ ] 0.1. Выяснить, у каких пользователей есть роль `ОтклонениеОтУсловийПродаж`.
      Запросом по `РегистрСведений` состава ролей или через список пользователей ИБ.
- [ ] 0.2. Если роль есть у рядовых менеджеров — **эскалировать заказчику**: при решении
      «роли не трогаем» ограничение для них не сработает. Получить письменное подтверждение
      либо пересмотр решения №4.
- [ ] 0.3. Проверить текущие значения ФО `ИспользоватьРучныеСкидкиВПродажах`
      и `ИспользоватьОграниченияРучныхСкидокВПродажахПоСоглашениям`.
- [ ] 0.4. Посчитать, сколько действующих соглашений имеют пустой `ПроцентРучнойСкидки`
      и снятый `ОграничиватьРучныеСкидки` — оценить объём работ этапа 2.
- [ ] 0.5. Проверить заполненность `СоглашенияОЦенообразовании.МинимальнаяЦена`:
      сколько активных записей, какой процент номенклатуры покрыт. Определяет
      реальную ценность этапа 3.
- [ ] 0.6. Найти документ из инцидента («продали ниже себестоимости»), зафиксировать
      его как эталонный кейс регресса: после внедрения такой документ не должен проводиться.

**Результат этапа:** отчёт в `work/task_FT-101/discovery.md` с ответом на вопрос —
сработает ли выбранное решение на реальных данных.

## Этап 1. Включение типового механизма (контур 1)

Работы только в режиме «Предприятие», конфигурация не меняется.

- [ ] 1.1. Включить ФО `ИспользоватьРучныеСкидкиВПродажах`
      (НСИ и администрирование → Продажи), если выключена.
- [ ] 1.2. Включить ФО `ИспользоватьОграниченияРучныхСкидокВПродажахПоСоглашениям`.
- [ ] 1.3. Убедиться, что в форме соглашения с клиентом появилась группа
      ограничения ручных скидок (`ОграничиватьРучныеСкидки`, `ПроцентРучнойСкидки`,
      `ПроцентРучнойНаценки`).
- [ ] 1.4. На одном тестовом соглашении: взвести `ОграничиватьРучныеСкидки`,
      задать `ПроцентРучнойСкидки` = 10.
- [ ] 1.5. Проверить блокировку: заказ клиента по этому соглашению со скидкой 15%
      не должен проводиться, сообщение должно указывать на строку ТЧ.
- [ ] 1.6. Проверить обратное: скидка 5% проводится без замечаний.

## Этап 2. Заполнение лимитов в соглашениях

- [ ] 2.1. Согласовать с заказчиком матрицу лимитов: единый % для всех соглашений
      или разные по сегментам/ценовым группам.
- [ ] 2.2. **Проверить связку флага и процента:** взведённый `ОграничиватьРучныеСкидки`
      при пустом `ПроцентРучнойСкидки` означает лимит 0% — заблокируется любая скидка.
      Заполнять оба реквизита одной операцией.
- [ ] 2.3. Заполнить лимиты в действующих соглашениях (групповая обработка
      или обработка заполнения — по объёму из п. 0.4).
- [ ] 2.4. При необходимости детализации — заполнить ТЧ `ЦеновыеГруппы`
      с лимитами в разрезе ценовых групп.
- [ ] 2.5. Согласовать с заказчиком регламент: кто и на каком основании ставит
      флаг `Согласован`, снимающий проверку (Риск 2).
- [ ] 2.6. Прогнать эталонный кейс из п. 0.6 — убедиться, что документ инцидента
      теперь блокируется. Если он проходит — причина была не в проценте скидки,
      и контур 1 инцидент не закрывает; переходить к этапу 3 обязательно.

## Этап 3. Контроль минимальной цены (контур 2, доработка)

### 3.1. Метаданные

- [ ] 3.1.1. Создать константу `КонтролироватьМинимальнуюЦенуПродажи` (Булево).
- [ ] 3.1.2. Создать ФО `КонтролироватьМинимальнуюЦенуПродажи` на этой константе.
- [ ] 3.1.3. Вывести константу в форму настроек продаж.

### 3.2. Программный интерфейс чтения минимальных цен

- [ ] 3.2.1. В `ОбщийМодуль.ЦенообразованиеСервер` добавить **экспортную** функцию
      `МинимальныеЦеныПоТоварам(ТаблицаТоваров, Контрагент, Дата)`.
      Возвращает таблицу Номенклатура + ВидЦены + МинимальнаяЦена.
- [ ] 3.2.2. Запрос строить **одним пакетом** на всю ТЧ (соединение с таблицей-параметром),
      без цикла по строкам.
- [ ] 3.2.3. Обязательно использовать `СрезПоследних(&Дата, Активное)` — регистр
      периодический (Day). Не копировать подход существующей `ПолучитьИндивидуальнуюЦену`,
      которая срез не использует (дефект, см. п. 5.3 architecture.md).
- [ ] 3.2.4. Заголовочный комментарий по стандарту ИТС, типы параметров указать
      фактические: `Контрагент` — `СправочникСсылка.Контрагенты` (не Партнёры).

### 3.3. Модуль проверки

- [ ] 3.3.1. Создать `ОбщийМодуль.КонтрольМинимальнойЦеныСервер` (Сервер, Вызов сервера — нет).
- [ ] 3.3.2. Реализовать экспортную `ПроверитьМинимальныеЦены(ДокументОбъект, Отказ)`.
- [ ] 3.3.3. `<validation>` Ранний выход: ФО выключена или ТЧ `Товары` пуста.
- [ ] 3.3.4. `<security>` Ранний выход при роли `ОтклонениеОтУсловийПродаж`
      через `ПраваПользователяПовтИсп.ОтклонениеОтУсловийПродаж()` — not delete.
- [ ] 3.3.5. `<query>` Получить минимальные цены вызовом из п. 3.2.1.
- [ ] 3.3.6. `<processing>` Отобрать строки: `МинимальнаяЦена > 0` И `Цена < МинимальнаяЦена`.
- [ ] 3.3.7. `<error>` По каждой нарушенной строке — `СообщитьПользователю`
      с `ОбщегоНазначенияКлиентСервер.ПутьКТабличнойЧасти("Товары", НомерСтроки, "Цена")`,
      выставить `Отказ = Истина` — not delete.
- [ ] 3.3.8. Разметить блоки семантическими якорями по `CONVENTIONS.md`.

### 3.4. Встраивание в документы

- [ ] 3.4.1. `Документ.ЗаказКлиента`, модуль объекта, `ОбработкаПроверкиЗаполнения` —
      добавить вызов `КонтрольМинимальнойЦеныСервер.ПроверитьМинимальныеЦены(ЭтотОбъект, Отказ)`.
- [ ] 3.4.2. То же для `Документ.РеализацияТоваровУслуг`.
- [ ] 3.4.3. Проверить, что вызов не ломает типовую логику проверки заполнения
      (вызов добавляем, существующий код не переписываем).

## Этап 4. Тестирование

- [ ] 4.1. Контур 1: скидка в пределах лимита — проводится.
- [ ] 4.2. Контур 1: скидка выше лимита — блокируется, сообщение ведёт на строку ТЧ.
- [ ] 4.3. Контур 1: пользователь с ролью `ОтклонениеОтУсловийПродаж` — проходит
      (ожидаемое поведение по решению №4, зафиксировать как норму, не как дефект).
- [ ] 4.4. Контур 2: цена ниже `МинимальнаяЦена` — блокируется.
- [ ] 4.5. Контур 2: цена равна `МинимальнаяЦена` — проводится (граница включительно).
- [ ] 4.6. Контур 2: записи в регистре нет — проводится без ошибок (не блокируем
      то, для чего порог не задан).
- [ ] 4.7. Контур 2: запись есть, но `Активное = Ложь` — порог игнорируется.
- [ ] 4.8. Контур 2: несколько записей на разные даты — берётся актуальная на дату
      документа (проверка корректности `СрезПоследних`).
- [ ] 4.9. Комбинация: скидка в пределах лимита, но цена ниже минимальной —
      документ блокируется контуром 2. **Ключевой тест**, ради него делался этап 3.
- [ ] 4.10. Эталонный кейс инцидента из п. 0.6 — блокируется.
- [ ] 4.11. Производительность: документ на 100+ строк — замерить, что проверка
      не даёт заметной задержки при проведении (следствие пакетного запроса).
- [ ] 4.12. Регресс: проведение документов без скидок и без записей в регистре
      не изменило поведения.
