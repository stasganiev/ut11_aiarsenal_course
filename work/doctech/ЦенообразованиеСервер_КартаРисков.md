# Карта рисков: ПолучитьИтоговуюЦенуСоСкидкой

**Модуль:** `ЦенообразованиеСервер`  
**Функция:** `ПолучитьИтоговуюЦенуСоСкидкой`  
**Дата анализа:** 2026-05-05  
**Аналитик:** QA (AI-ассистент)

---

## Аннотация

Функция реализует цепочку: базовая цена → замена индивидуальной (если ФО включена) → расчёт скидки → ограничение потолком → итоговая цена.  
Ошибка на любом звене означает либо финансовый ущерб (неверный счёт клиенту), либо искажение управленческой аналитики. Риски отсортированы по убыванию критичности.

---

## Карта рисков

### Р-01 — Деление на ноль при нулевом знаменателе в формуле

| Поле | Значение |
|------|----------|
| **Риск** | Нет деления на ноль в явном виде, однако `ПроцентСкидки = 100` при `ПотолокСкидки = 100` даёт `ИтоговаяЦена = 0`, что равносильно передаче товара бесплатно |
| **Условие** | Константа `МаксимальнаяСкидкаПоУмолчанию = 100` и `РасчётСкидок.РассчитатьСкидку(...)` возвращает ≥ 100; нет технического деления, но бизнес-результат катастрофичен |
| **Критичность** | **Блокирующий** — цена товара становится 0, документ продажи проведётся без ошибки, деньги не будут получены |
| **Бизнес-последствие** | Менеджер оформляет отгрузку по цене 0 руб.; клиент получает товар бесплатно; выявляется только при сверке или инвентаризации |
| **Тест-кейс** | Базовая цена = 5000 руб., `МаксимальнаяСкидкаПоУмолчанию` = 100, `РассчитатьСкидку` возвращает 100. Ожидаемый результат: **0 руб.** Нужно: бросить исключение или вернуть минимально допустимую цену, а не 0 |
| **Реализация** | Оба — автотест фиксирует числовой результат 0; ручной проверяет поведение интерфейса (создаётся ли документ с нулевой ценой) |
| **Зависимость от внешних данных** | Да — `Константы.МаксимальнаяСкидкаПоУмолчанию` = 100 в базе данных |

### Р-02 — Константа `МаксимальнаяСкидкаПоУмолчанию` не заполнена (Неопределено / NULL)

| Поле | Значение |
|------|----------|
| **Риск** | `Константы.МаксимальнаяСкидкаПоУмолчанию.Получить()` возвращает `Неопределено` (тип не установлен, база новая); сравнение `ПроцентСкидки > Неопределено` в 1С не бросает исключение, а возвращает `Ложь` — потолок не срабатывает |
| **Условие** | Константа не была инициализирована при запуске новой базы или была сброшена вручную; нет механизма проверки на `Неопределено` до сравнения |
| **Критичность** | **Высокий** — любая скидка от `РассчитатьСкидку`, даже 95%, применяется без ограничения; цена занижается произвольно |
| **Бизнес-последствие** | Менеджеры видят в документах заниженные цены; аналитики принимают решения по некорректной марже; потеря выручки незаметна без аудита |
| **Тест-кейс** | Константа не задана (`Получить()` = `Неопределено`), `РассчитатьСкидку` = 80, базовая цена = 1000. Ожидаемый результат при текущем коде: **200 руб.** Корректный: должна применяться скидка не выше разумного предела (например, 30%) → **700 руб.** |
| **Реализация** | Автотест — сценарий детерминирован; подменить возврат константы на `Неопределено` через тестовый дубль |
| **Зависимость от внешних данных** | Да — константа `МаксимальнаяСкидкаПоУмолчанию` должна быть незаполнена в тестовой базе |

### Р-03 — `РасчётСкидок.РассчитатьСкидку` возвращает отрицательное значение

| Поле | Значение |
|------|----------|
| **Риск** | Внешний модуль `РасчётСкидок` возвращает отрицательный процент (например, −10 — наценка вместо скидки); нет проверки на `< 0`; формула `БазоваяЦена * (1 - (-10) / 100)` увеличивает цену незаметно |
| **Условие** | В `РасчётСкидок` настроена акция-наценка; или договор предполагает надбавку; или модуль содержит баг, возвращающий отрицательный процент |
| **Критичность** | **Высокий** — цена завышается без ведома менеджера и клиента; конфликт при оплате; при отчёте «Анализ цен» руководитель видит цены выше прайса, что вводит в заблуждение |
| **Бизнес-последствие** | Клиент выставляет претензию по цене; или аналитик принимает решение о неверной марже; репутационный и финансовый ущерб |
| **Тест-кейс** | Базовая цена = 1000, `РассчитатьСкидку` = −10, `ПотолокСкидки` = 30. Условие `−10 > 30` → Ложь, ограничение не применяется. Итоговая цена = `1000 * (1 − (−10)/100)` = **1100 руб.** Ожидаемый корректный результат: 1000 руб. (наценка должна игнорироваться или обрабатываться отдельной логикой) |
| **Реализация** | Автотест |
| **Зависимость от внешних данных** | Да — в `РасчётСкидок` должна быть настройка, возвращающая отрицательный процент |

### Р-04 — Несколько активных соглашений об индивидуальной цене для одного контрагента/номенклатуры

| Поле | Значение |
|------|----------|
| **Риск** | Запрос к `РегистрСведений.СоглашенияОЦенообразовании` не содержит `ПЕРВЫЕ 1` и не упорядочен; при нескольких активных записях `Выбрать().Следующий()` вернёт первую строку в порядке физического хранения — результат недетерминирован |
| **Условие** | Для одной пары (Контрагент, Номенклатура) создано более одной записи с `Активное = Истина`; возникает при дублировании или при ошибке ввода данных |
| **Критичность** | **Высокий** — функция вернёт разную индивидуальную цену в зависимости от порядка строк в таблице; цена нестабильна между запусками и серверами |
| **Бизнес-последствие** | Два одинаковых заказа одного клиента могут иметь разные цены; аналитик в «Анализе цен» видит хаотичные цифры; клиент замечает расхождение |
| **Тест-кейс** | В регистре `СоглашенияОЦенообразовании` — две активных записи для (Контрагент = «Ромашка», Номенклатура = «Товар А»): цена 900 и 800. Вызов функции при `УчитыватьИндивидуальныеЦены = Истина`. Ожидаемый результат: детерминированное значение (например, минимальная или последняя по дате) — на практике будет 800 или 900 непредсказуемо |
| **Реализация** | Оба — автотест фиксирует конкретное значение; ручной проверяет, что UI не позволяет создать дубль |
| **Зависимость от внешних данных** | Да — две записи `СоглашенияОЦенообразовании` с `Активное = Истина` для одной пары |

### Р-05 — ФО `УчитыватьИндивидуальныеЦены` выключена: индивидуальная цена ниже базовой игнорируется

| Поле | Значение |
|------|----------|
| **Риск** | При выключенной ФО контрагент, которому договорились дать цену 800 руб. при базовой 1200 руб., получает счёт по 1200 руб.; функция не сигнализирует об этом |
| **Условие** | Администратор отключил `УчитыватьИндивидуальныеЦены`; в регистре есть активные соглашения; менеджеры не знают об отключении ФО |
| **Критичность** | **Высокий** — клиент получает счёт дороже договорённости; конфликт; возможен отказ от оплаты |
| **Бизнес-последствие** | Клиент выставляет претензию; менеджер обнаруживает разрыв между CRM-договорённостью и выставленным счётом только после жалобы |
| **Тест-кейс** | ФО `УчитыватьИндивидуальныеЦены` = Ложь. Базовая цена = 1200, в соглашении индивидуальная = 800. Ожидаемый результат при текущем коде: **1200 руб.** (соглашение проигнорировано). Должен быть хотя бы журнал предупреждения |
| **Реализация** | Ручной — необходима проверка пользовательского сценария «у клиента есть соглашение, но ФО выключена» |
| **Зависимость от внешних данных** | Да — запись в `СоглашенияОЦенообразовании` + ФО = Ложь |

### Р-06 — ФО `УчитыватьИндивидуальныеЦены` включена: индивидуальная цена выше базовой — клиент переплачивает

| Поле | Значение |
|------|----------|
| **Риск** | Условие `ИндивидуальнаяЦена > 0` не защищает от случая, когда индивидуальная цена выше базовой; покупатель получает счёт по завышенной цене |
| **Условие** | В `СоглашенияОЦенообразовании` записана цена 1500, базовая = 1200; менеджер внёс данные ошибочно, или соглашение устарело |
| **Критичность** | **Средний** — прямой финансовый ущерб клиенту; при массовом использовании — репутационный риск |
| **Бизнес-последствие** | Клиент переплачивает; доверие к ценообразованию подрывается; аналитик в «Анализе цен» видит завышенную маржу, принимает неверные решения |
| **Тест-кейс** | Базовая цена = 1200, `ИндивидуальнаяЦена` = 1500, скидка = 0, ФО = Истина. Итоговая цена = **1500 руб.** Корректный сценарий — применять минимум из двух или предупреждать |
| **Реализация** | Автотест |
| **Зависимость от внешних данных** | Да — запись `СоглашенияОЦенообразовании` с `ИндивидуальнаяЦена` > базовой цены |

### Р-07 — Базовая цена в регистре — устаревшая (срез последних возвращает старую цену)

| Поле | Значение |
|------|----------|
| **Риск** | Параметр `Дата` передаётся как прошедшая дата (например, дата договора, а не текущая дата); `СрезПоследних(&Дата, ...)` вернёт цену, актуальную на ту дату — возможно, более низкую или более высокую |
| **Условие** | Вызывающий код передаёт в параметр `Дата` дату подписания договора вместо текущей даты сеанса; или дату начала акции |
| **Критичность** | **Средний** — клиент может получить счёт по неактуальной цене; сумма заказа в аналитике некорректна |
| **Бизнес-последствие** | При росте цен — недополучение выручки; при снижении — клиент переплачивает; в «Анализе цен» сравнения ведутся по разным базовым ценам |
| **Тест-кейс** | В регистре: цена на 2026-01-01 = 1000, на 2026-04-01 = 1200. Вызов с `Дата = 2026-01-15`. Ожидаемый результат: **1000 руб.** Если реальная цена должна быть 1200 — ошибка ценообразования |
| **Реализация** | Ручной — требуется проверка конкретных форм документов, какую дату они передают |
| **Зависимость от внешних данных** | Да — два среза цены в регистре `ЦеныНоменклатуры` с разными датами |

### Р-08 — `РасчётСкидок.РассчитатьСкидку` бросает исключение

| Поле | Значение |
|------|----------|
| **Риск** | Внешний вызов `РасчётСкидок.РассчитатьСкидку(...)` не обёрнут в `Попытка`; при любом исключении внутри модуля `РасчётСкидок` вся цепочка прерывается с ошибкой платформы |
| **Условие** | В модуле `РасчётСкидок` ошибка соединения с внешней системой акций; или некорректный параметр `СуммаЗаказа` (например, `Неопределено`); или ошибка в алгоритме акций |
| **Критичность** | **Средний** — пользователь видит системную ошибку 1С; не может оформить документ продажи до устранения |
| **Бизнес-последствие** | Менеджер не может создать заказ; звонит в поддержку; продажи встают на время диагностики; особенно критично в пиковые периоды |
| **Тест-кейс** | Передать `СуммаЗаказа = Неопределено`. Ожидаемый результат при наличии защиты: вернуть базовую цену без скидки. Текущий результат: исключение платформы или ошибка в `РасчётСкидок` |
| **Реализация** | Автотест — подменить `РасчётСкидок.РассчитатьСкидку` на вызов, бросающий исключение |
| **Зависимость от внешних данных** | Нет — воспроизводится через передачу некорректных параметров |

### Р-09 — `СуммаЗаказа = 0`: скидка не рассчитывается корректно для пороговых акций

| Поле | Значение |
|------|----------|
| **Риск** | `СуммаЗаказа = 0` передаётся при создании новой строки документа до заполнения всех позиций; модуль `РасчётСкидок` может вернуть 0% вместо актуальной скидки — покупатель теряет скидку за объём |
| **Условие** | Форма документа вызывает функцию на событие «При изменении номенклатуры» до расчёта суммы; или передаётся явно `СуммаЗаказа = 0` |
| **Критичность** | **Средний** — клиент теряет скидку, на которую рассчитывал; конфликт при выставлении счёта |
| **Бизнес-последствие** | Клиент видит цену без объёмной скидки; менеджер вынужден вручную корректировать; аналитик видит некорректные данные по суммарным скидкам |
| **Тест-кейс** | Контрагент с договором, дающим скидку 15% при сумме заказа > 50 000 руб. Вызов с `СуммаЗаказа = 0`. `РассчитатьСкидку` = 0, потолок не влияет. Базовая цена = 2000. Итого: **2000 руб.** вместо **1700 руб.** |
| **Реализация** | Оба — автотест проверяет числовой результат; ручной проверяет поведение формы при поэтапном заполнении |
| **Зависимость от внешних данных** | Да — договор с пороговой скидкой в `РасчётСкидок` |

### Р-10 — Индивидуальная цена в соглашении равна нулю: замена не происходит, но запись есть

| Поле | Значение |
|------|----------|
| **Риск** | Условие `ИндивидуальнаяЦена > 0` корректно защищает от нулевых значений, однако менеджер, внёсший нулевую индивидуальную цену как «договорную», считает, что клиенту дана особая цена — система молча игнорирует запись |
| **Условие** | Менеджер создаёт соглашение с `ИндивидуальнаяЦена = 0` («уточним позже»); запись активна; функция ведёт себя как при отсутствии соглашения |
| **Критичность** | **Низкий** — пользователь не получает ошибки; поведение технически корректно, но создаёт ложные ожидания |
| **Бизнес-последствие** | Менеджер уверен, что клиенту применяется особая цена, но в документе стоит базовая; обнаруживается на этапе сверки с клиентом |
| **Тест-кейс** | `СоглашенияОЦенообразовании`: Контрагент = «Лютик», Номенклатура = «Товар Б», `ИндивидуальнаяЦена = 0`, `Активное = Истина`. Базовая цена = 900, скидка = 0. Итого: **900 руб.** — соглашение проигнорировано без предупреждения |
| **Реализация** | Ручной — требует проверки UI: есть ли предупреждение при сохранении нулевой цены в соглашении |
| **Зависимость от внешних данных** | Да — запись `СоглашенияОЦенообразовании` с `ИндивидуальнаяЦена = 0` и `Активное = Истина` |
