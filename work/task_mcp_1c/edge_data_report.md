# Тестовые данные для граничных случаев `ЦенообразованиеРасчет.РассчитатьЦену`

- **База:** `C:\dev\bases1c\ut11aiarsenal_course` (УТ 11.5), подключение через MCP `onec-data` (OData).
- **Источник сценариев:** [work/tests/edge/test_escapes.md](../tests/edge/test_escapes.md), группа **ПОДТВЕРЖДЕНО** (13 находок).
- **Префикс всех созданных объектов:** `EDGE_` (в `Description`), у документов без такого реквизита — маркер `EDGE` в начале `Комментарий`.

## 1. Ключевой вывод перед данными: код и база — из разных миров

Модуль [ЦенообразованиеРасчет](../../src/CommonModules/ЦенообразованиеРасчет/Ext/Module.bsl) — синтетический учебный код. Проверка через OData показала, что реальная конфигурация УТ 11.5 **не содержит** объектов, на которые опирается код:

| В коде модуля | В реальной базе |
|---|---|
| `Соглашение.МинимальнаяЦена` | нет такого реквизита у `Catalog_СоглашенияСКлиентами` |
| `Соглашение.ПравилоОкругления` (перечисление `ПравилаОкругления`) | нет; у `ВидыЦен` есть смысловой аналог: `Округлять`/`ОкруглятьВБольшуюСторону`/`ТочностьОкругления` |
| `Справочник.Акции` (поля `Товар`, `ПроцентСкидки`, `ДатаНачала`/`ДатаОкончания`) | `Catalog_Акции` существует, но это акцизные марки ЕГАИС — другая предметная область |
| `РегистрСведений.ИсторияРасчётаЦен` | не существует |
| `Перечисления.КатегорииКлиентов.VIP/Новый` | у `Catalog_Контрагенты` есть строковое поле `Категория` и булево `VIP`, но не перечисление |
| `РегистрНакопления.Закупки.Обороты(Контрагент)` | `AccumulationRegister_Закупки` существует, но состав измерений не проверялся |

Из-за этого **6 из 13** подтверждённых сценариев физически невоспроизводимы через данные этой базы напрямую — они привязаны к полям, которых нет. Ниже — честная карта: что создано, что покрывает, что нет.

## 2. Системное ограничение MCP-сервера, обнаруженное в процессе

**Запись в табличные части документов (`create_document`/`update_document` со вложенным массивом строк) стабильно возвращает HTTP 500**, независимо от состава полей и конкретного документа. Проверено на:
- `Document_УстановкаЦенНоменклатуры.Товары` — с новым видом цены и с боевым видом цены — оба раза 500.
- `Document_РеализацияТоваровУслуг.Товары` — минимальный набор полей (`Номенклатура_Key`, `Количество`, `Цена`, `Сумма`) — тоже 500.

При этом создание/обновление **шапок** документов, элементов справочников и мягкое удаление (`set_deletion_mark`) работают надёжно. Физическое удаление документа (`delete_document`) тоже вернуло 500 — использовалась пометка на удаление вместо него.

**Следствие:** ни один сценарий, требующий реальных строк товаров с ценами и скидками в документе (например, воспроизведение точного расчёта `РассчитатьЦену` через проведение документа), через этот MCP создать не удалось. Созданы только заготовки — шапки документов и справочные объекты, которые фиксируют условия сценария (даты, ссылки, реквизиты), но не позволяют довести документ до проведения с табличной частью.

## 5. Процедура очистки

Все объекты помечены префиксом `EDGE_` в `Description` (документы — маркером `EDGE` в начале `Комментарий`), поэтому безопасно находятся фильтром `substringof('EDGE_',Description)` / `substringof('EDGE',Комментарий)`.

**Порядок удаления** (сначала документы, потом справочники — из-за ссылочной целостности):

1. `Document_РеализацияТоваровУслуг`: `14eed011-...`, `14eed016-...`, `14eed017-...` — через `set_deletion_mark(mark=true)`, затем окончательное удаление штатной обработкой «Удаление помеченных объектов» в Конфигураторе/Предприятии (физическое `delete_document` через MCP на момент проверки возвращало HTTP 500 — то же ограничение, что и запись табличных частей).
2. `Catalog_СоглашенияСКлиентами`: `14eed014-...`, `14eed015-...`
3. `Catalog_Контрагенты`: `14eed00a-...`, `14eed00c-...`
4. `Catalog_ВидыЦен`: `14eed009-...`
5. `Catalog_Номенклатура`: `14eed007-...`, `14eed008-...`

Повторный запуск создания данных безопасен: все `create_catalog_item`/`create_document` вызовы создают новые элементы (в 1С через OData нет upsert по `Description`), поэтому перед повторным прогоном нужно сначала выполнить очистку по списку выше — иначе появятся дубли с одинаковым префиксом `EDGE_`.

## 6. Что нужно доделать вручную (не через MCP)

1. **Записать цены** `EDGE_Товар_Дорогой=1000`, `EDGE_Товар_Дешёвый50=50` по виду цены `EDGE_ВидЦены_Розница` на 01.01.2026 — через документ «Установка цен номенклатуры» в Предприятии (табличная часть не создаётся через MCP).
2. **Добавить строки товаров** в документы ТД00-000002 и ТД00-000003, чтобы довести их до проведения и увидеть реальный расчёт `РассчитатьЦену`/`РассчитатьЦеныДокумента`.
3. Если модуль `ЦенообразованиеРасчет` предполагается реально подключить к этой конфигурации — потребуется либо доработка конфигурации (добавить реквизиты `МинимальнаяЦена`/`ПравилоОкругления` в `СоглашенияСКлиентами`, справочник акций с нужной структурой, регистр `ИсторияРасчётаЦен`), либо явное указание, что модуль тестируется изолированно (например, через xUnitFor1C с моками, без обращения к реальным объектам конфигурации).
