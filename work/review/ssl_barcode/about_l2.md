# Генерация штрихкодов — уровень 2, для разработчика

Для тех, кто будет вызывать механизм из прикладного кода или разбираться,
почему он не работает. Вводное объяснение — `about_l1.md`, навигационная
карта с точками входа — `map.md`.

---

## 1. Архитектура

Четыре слоя, вызов идёт строго сверху вниз, обратных вызовов нет:

```
  Прикладной код (печать этикеток, ККТ, СБП, дисплеи, фискальные документы)
        │  структура параметров
        ▼
  ГенерацияШтрихкода — программный интерфейс
        │  фасад: валидация не делается, идёт диспетчеризация
        ├──────────────► ГенерацияШтрихкодаСерверПовтИсп  (кэш подключения)
        │                       │
        │                       ▼
        │                 ВнешниеКомпонентыБПО | ВнешниеКомпонентыСервер
        │                       │              | ОбщегоНазначения (фолбэк)
        │                       ▼
        │                 ОбщийМакет.КомпонентаПечатиШтрихкодов
        ▼
  Адаптеры протокола (внутри того же модуля)
    ├─ через свойства объекта   (путь по умолчанию)
    └─ через XML-документ       (флаг НовыйВызовКомпоненты)
        │
        ▼
  Внешняя компонента Barcode — рендеринг
```

Три архитектурных решения, которые определяют всё поведение:

**Фасад с адаптерами протокола.** Наружу торчит одна функция генерации, но
под ней два принципиально разных способа общения с компонентой: раскладка
по свойствам объекта и сборка XML-документа. Выбор — по флагу в структуре
параметров. Это классический адаптер: контракт наружу один, реализации две,
и они не эквивалентны (см. п.5, шаг 6).

**Кэш вынесен в отдельный модуль.** Платформа умеет кэшировать возвращаемые
значения только на уровне модуля целиком, а не отдельной функции. Кэшировать
надо ровно подключение компоненты — но не генерацию, которая каждый раз даёт
разный результат. Отсюда модуль-спутник из одной функции: единственный способ
получить кэширование на одну операцию, не задев остальные.

**Двойная лояльность БСП/БПО.** Механизм поставляется и в составе БСП
(Библиотека стандартных подсистем), и в составе БПО (Библиотека подключаемого
оборудования), и должен работать в конфигурации с любой комбинацией. Отсюда
проверки существования подсистем в рантайме и получение модулей через
`Вычислить`, а не прямыми ссылками.

## 2. Модули и зоны ответственности

### `ГенерацияШтрихкода`

Сервер, `ReturnValuesReuse = DontUse`, не привилегированный, без `ServerCall`
(вызывать с клиента напрямую нельзя — только через свой серверный контекст).

| Область | Слой | Ответственность |
|---|---|---|
| `ПрограммныйИнтерфейс` | ПИ | Контракт наружу: фабрика структуры параметров, генерация изображения, частный случай для QR |
| `СлужебныйПрограммныйИнтерфейс` | Служебный | Подключение и первичная настройка компоненты, паспорт компоненты (имя объекта + путь к макету) |
| `СлужебныеПроцедурыИФункции` | Внутренний | Два адаптера протокола + резолвер модуля общего назначения |

Модуль совмещает фасад и адаптеры. Для БСП это норма — механизм слишком
мал, чтобы разносить по отдельным модулям.

### `ГенерацияШтрихкодаСерверПовтИсп`

Сервер, **`ReturnValuesReuse = DuringSession`** (проверено в
`src/CommonModules/ГенерацияШтрихкодаСерверПовтИсп.xml:20`).

Зона ответственности ровно одна — кэширование подключённой компоненты на
сеанс. Тело функции — единственная строка-переадресация обратно в
`ГенерацияШтрихкода`. Логики нет и быть не должно.

Параметр `ТипПлатформыКомпоненты` в теле **не используется** — он существует
исключительно как ключ кэша. Смысл: на разных типах платформы (Windows/Linux,
x86/x64) компонента разная, и один закэшированный объект на все платформы
был бы неверен. Выглядит как мёртвый параметр, но удалять его нельзя.

Клиентских модулей у механизма нет — генерация только серверная.

## 3. Модель данных

**Модели данных в привычном смысле у механизма нет.** Ни справочников, ни
регистров, ни констант, ни ролей. Состав подсистемы — три элемента:
общий макет с компонентой и два общих модуля.

Механизм stateless: ничего не пишет в базу, ничего оттуда не читает,
результат не кэширует. Одинаковый вход всегда даёт одинаковый выход,
изображения генерируются заново при каждом обращении.

Вместо модели данных — три структуры-контракта, живущие только в памяти:

**Структура параметров** — вход. 19 полей, отдаётся фабрикой с заполненными
значениями по умолчанию. Группируются так:

| Группа | Поля |
|---|---|
| Данные | `Штрихкод`, `ТипВходныхДанных` (0 — строка, 1 — base64) |
| Геометрия | `Ширина`, `Высота`, `УголПоворота`, `Масштабировать`, `СохранятьПропорции`, `ВертикальноеВыравнивание` |
| Формат | `ТипКода` (99 — автовыбор), `GS1DatabarКоличествоСтрок`, `УровеньКоррекцииQR` |
| Оформление | `ОтображатьТекст`, `РазмерШрифта`, `ПрозрачныйФон`, `Инвертирован`, `УбратьЛишнийФон` |
| Логотип QR | `ЛоготипКартинка` (base64 PNG), `ЛоготипРазмерПроцентОтШК` |
| Служебное | `НовыйВызовКомпоненты` |

Два поля логотипа фабрика вставляет **без значения** — они `Неопределено`,
а не пустая строка. Учитывай при собственных проверках.

**Структура результата** — выход, три поля: `Результат` (Булево, код возврата
компоненты = 0), `ДвоичныеДанные` (PNG), `Картинка`. Последние два остаются
`Неопределено`, если компонента вернула пустой результат.

**Паспорт компоненты** — два поля: имя объекта `"Barcode"` и путь
`"ОбщийМакет.КомпонентаПечатиШтрихкодов"`.

Связь между ними линейная: параметры → компонента → результат. Никаких
ссылок, ключей и агрегатов.

## 4. Экспортный API

Модуль `ГенерацияШтрихкода`, область `ПрограммныйИнтерфейс`:

**`ПараметрыГенерацииШтрихкода()` → Структура**
Фабрика структуры параметров с дефолтами. Аргументов нет.
Вызывать всегда — при обновлении БСП набор полей меняется, и структура,
собранная вручную, отвалится на первом же обращении к новому полю.

**`ИзображениеШтрихкода(ПараметрыШтрихкода) → Структура`**
Основная точка входа. Принимает структуру от фабрики, возвращает результат
из трёх полей.
Контракт по ошибкам: **выбрасывает исключение**, если компонента не
подключилась (с предварительной записью в журнал регистрации). Если
компонента подключилась, но сгенерировать не смогла — исключения не будет,
вернётся структура с `Результат = Ложь` и незаполненной картинкой.
Проверять надо оба случая.

**`ДанныеQRКода(QRСтрока, УровеньКоррекции, Размер) → ДвоичныеДанные`**
Частный случай для QR: внутри берёт фабрику, ставит тип кода 16, квадратный
размер и `УбратьЛишнийФон = Истина`.
`УровеньКоррекции` — 0/1/2/3 (7/15/25/35 % допустимых повреждений).
`Размер` — сторона в пикселях; если минимально возможный QR больше — код
не сформируется.
Контракт по ошибкам **другой**: исключение гасится внутри и пишется в журнал.
Ловушка: при ошибке переменная результата остаётся неинициализированной,
и наружу уходит `Неопределено`. Молчаливый отказ — проверяй возврат.

Область `СлужебныйПрограммныйИнтерфейс` — экспортное, но не для прикладного
кода: подключение компоненты (возвращает объект компоненты или
`Неопределено`) и паспорт компоненты. Трогать при интеграции с БПО или
при отладке подключения.

Не экспортные, снаружи недоступны: два адаптера протокола и резолвер модуля
общего назначения.

## 5. Жизненный цикл

Сценарий — вывод штрихкода в печатную форму документа
(`ШтрихкодированиеПечатныхФорм`, реальный код):

1. **Функциональная опция.** Прикладной код проверяет
   `ИспользоватьШтрихкодированиеПечатныхФормОбъектов`. Если выключена —
   рисунок штрихкода удаляется из области макета, механизм не вызывается вовсе.

2. **Подготовка параметров.** Ширина и высота считаются из размеров рисунка
   в макете с переводом миллиметров в пиксели через эталонный макет;
   тип кода задан явно (Code128), подпись отключена.

3. **Вызов фасада.** Управление уходит в `ИзображениеШтрихкода`.

4. **Определение платформы.** Создаётся `Новый СистемнаяИнформация`, тип
   платформы приводится к строке и передаётся в кэширующий модуль как ключ.

5. **Подключение компоненты** — только на первом вызове за сеанс, дальше из
   кэша. Развилка:
   - есть подсистема `ПоддержкаОборудования` → через БПО (в УТ 11 идёт этот путь);
   - иначе БСП: снимается безопасный режим, проверяется доступность
     разделённых данных (важно для облачной работы), подключение через
     подсистему внешних компонент; если не вышло — фолбэк напрямую из макета.

   Затем настройка шрифта: ищется Tahoma, иначе первый доступный перебором;
   размер жёстко 12.

   Если компонента не поднялась → запись в журнал + исключение. Конец.

6. **Выбор адаптера** по флагу `НовыйВызовКомпоненты`:

   - **Ложь (по умолчанию)** — раскладка по свойствам объекта, затем
     получение штрихкода. Здесь же работает **подтягивание размеров до
     минимально допустимых**: если запрошенная ширина/высота меньше минимума
     для этого формата — они увеличиваются. При `СохранятьПропорции = Истина`
     это делается в цикле с пересчётом второй стороны.
   - **Истина** — сборка XML-документа с параметрами, вызов генерации,
     разбор ответного XML, картинка приходит в base64.

   **Ключевое отличие: подтягивания размеров в XML-ветке нет.** Переключение
   флага на конфигурации с мелкими этикетками даст нечитаемые штрихкоды —
   без ошибок и без записей в журнале.

7. **Формирование результата.** Признак успеха = код возврата компоненты 0,
   двоичные данные, из них `Новый Картинка`.

8. **Использование.** Картинка кладётся в рисунок области макета, область
   выводится в табличный документ.

Ничего не сохраняется: следующая печать того же документа пройдёт весь цикл
заново, начиная с шага 2.

## 6. Связи с другими подсистемами

### От чего зависит

| Зависимость | Характер | Что будет при отсутствии |
|---|---|---|
| `ОбщийМакет.КомпонентаПечатиШтрихкодов` | **Жёсткая** | Механизм неработоспособен |
| `ОбщегоНазначения` (БСП) | Жёсткая, но через `Вычислить` | Код основного языка, проверка подсистем, фолбэк подключения из макета |
| `СтандартныеПодсистемы.ВнешниеКомпоненты` | Мягкая | Есть фолбэк — подключение напрямую из макета |
| `ПоддержкаОборудования` (БПО) | Мягкая, взаимоисключающая с БСП-веткой | Идёт БСП-ветка подключения |
| `ОбработкаОшибок` (БСП) | Мягкая | Используется для подробного представления ошибки в журнале |

Все проверки существования подсистем — рантаймовые, модули берутся через
`Вычислить`. Поэтому статический анализ конфигурации связей не покажет,
и «поиск ссылок на объект» в конфигураторе здесь врёт.

Отдельно: `#Если НЕ МобильноеПриложениеСервер` вокруг работы с журналом
регистрации — механизм рассчитан на сборку в мобильном приложении, где
журнала нет.

### Кто зависит от него

Потребители в этой конфигурации (файлы и строки — в `map.md`):
печать этикеток и ценников, штрихкодирование печатных форм, чекопечатающие
устройства, дисплеи покупателя, СБП, шаблоны фискальных документов.

Отдельно — `УправлениеПечатью`: его функция получения данных QR-кода
**помечена устаревшей** и делегирует сюда. В новом коде вызывай механизм
напрямую.

Все потребители — на уровне подсистем БСП/БПО и прикладного кода; обратных
зависимостей у механизма на них нет. Точка расширения (переопределяемый
модуль) не предусмотрена: менять поведение можно только параметрами.

## Уверен (архитектурные принципы)

- Механизм stateless: не хранит данные, не кэширует изображения, не имеет
  объектов метаданных кроме макета и двух модулей.
- Разделение «модуль логики + модуль-спутник с кэшем на сеанс» — типовой
  приём БСП, обусловленный тем, что кэширование в платформе настраивается
  на модуль целиком.
- Синхронный, серверный, самостоятельно не стартует: подписок на события,
  регламентных заданий и обработчиков обновления ИБ нет.
- Фасад с двумя адаптерами протокола и выбором по флагу.
- Мягкие зависимости проверяются в рантайме через существование подсистем
  и `Вычислить` — ради работы в разных комбинациях БСП/БПО.
- Контракт «фабрика структуры параметров + функция, её принимающая»:
  структуру всегда берут у механизма, не собирают руками.
- Отсутствие переопределяемого модуля — влиять на поведение можно только
  через параметры.

## Проверено в этой выгрузке

Это я прочитал в исходниках, но сверь при обновлении БСП:

- `ReturnValuesReuse = DuringSession` у кэширующего модуля и `DontUse` у
  основного — `src/CommonModules/ГенерацияШтрихкодаСерверПовтИсп.xml:20`,
  `src/CommonModules/ГенерацияШтрихкода.xml:20`.
- Оба модуля: `Server = true`, `ServerCall = false`, `Privileged = false`.
- Состав подсистемы — ровно три элемента, без справочников, регистров и ролей.

## Требует проверки по конфигуратору

1. **Состав программного интерфейса** — три экспортные функции в области
   `ПрограммныйИнтерфейс`. В свежих версиях могли добавиться.
2. **19 полей структуры параметров и их дефолты** — набор рос от версии
   к версии. Особенно `ТипКода = 99`, `ПрозрачныйФон = Истина`,
   `УровеньКоррекцииQR = 1`, `ВертикальноеВыравнивание = 1`.
3. **Флаг `НовыйВызовКомпоненты`** — поле относительно новое, дефолт `Ложь`.
   Проверь, какая ветка отрабатывает у тебя, прежде чем закладываться на
   поведение с размерами.
4. **Числовые коды форматов** — 16 = QR, 4 = Code128, 18–24 = Datamatrix,
   25 = Aztec, 99 = авто. Список расширялся.
5. **Разное поведение по ошибкам** у основной функции генерации (исключение)
   и у функции QR (молчаливое `Неопределено`).
6. **Имя объекта компоненты и путь к макету** в паспорте компоненты.
7. **Имена методов БПО** — подключение компоненты и модуль общего назначения
   БПО версионируются отдельно от БСП.
8. **Состав потребителей** — приведён для этой сборки УТ 11.5.

## Практические заметки

- **Печать штрихкодов резко замедлилась.** Первым делом проверь
  `ReturnValuesReuse` у кэширующего модуля. Если сбито на `DontUse` —
  компонента подключается на каждый штрихкод. Всё работает правильно,
  но медленно, ошибок в журнале нет.
- **Не собирай структуру параметров вручную**, даже если нужно два поля.
  В конфигурации такой код есть — `ШтрихкодированиеПечатныхФорм` строит
  структуру из семи полей сам. Работает, потому что обе ветки адаптеров
  проверяют наличие полей перед чтением, но это хрупко: ветка по умолчанию
  читает часть полей **без проверки** (в том числе ширину, высоту, тип кода
  и признак отображения текста). Забыл поле из этого набора — исключение.
- **Проверяй результат.** Успешный вызов без исключения ещё не значит, что
  картинка есть: смотри признак успеха и заполненность картинки.
- **Логотип в QR** передаётся строкой base64 (в СБП — из библиотеки картинок),
  а размер задаётся процентом от штрихкода. Работает только для типа кода 16
  и требует высокого уровня коррекции — логотип физически перекрывает часть кода.
