## 1. Архитектура

### 1.1. Фундамент: что даёт платформа, а что — БСП

Понимание механизма начинается с этой границы. **БСП не изобретает обмен — она надстраивает оркестратор поверх штатного плана обмена платформы.**

Платформа предоставляет:

- объект метаданных «План обмена», узлы, состав объектов плана;
- **таблицу регистрации изменений** — служебную таблицу, которую платформа ведёт сама;
- механизмы `ПланыОбмена.ЗарегистрироватьИзменения` / `УдалитьРегистрациюИзменений`, чтение изменений через выборку;
- сообщения обмена (`ЗаписьСообщенияОбмена` / `ЧтениеСообщенияОбмена`) с нумерацией и подтверждением приёма;
- обработчики `ПриОтправкеДанныхПодписчику` / `ПриПолученииДанныхОтПодписчика` в модуле плана обмена;
- механизм РИБ поверх всего этого.

БСП добавляет всё, что платформа не покрывает:

| Слой БСП | Что решает |
|---|---|
| Декларативная регистрация | Правила «что кому отправлять» вынесены из кода в правила регистрации объектов (ПРО) |
| Транспорт | Единая абстракция над файлом, FTP, почтой, COM, веб-сервисом, внутренней публикацией |
| Конвертация | Перевод в нейтральный формат (КД2 XML-правила или КД3 EnterpriseData/XDTO) |
| Оркестрация | Сценарии, регламентные задания, длительные операции, прогресс |
| Настройка | Помощники, сопоставление объектов, согласование версий формата |
| Наблюдаемость | Состояния обменов, монитор проблем, архив сообщений, оценка производительности |
| Защита | Контроль зацикливания, приоритеты, отложенная запись узла |

**Практическое следствие.** Отлаживая обмен, всегда определяйте сначала, на каком уровне проблема. «Объект не уехал» — это либо не сработала регистрация (уровень БСП, ПРО), либо запись есть в таблице регистрации, но не прошла выгрузка (уровень конвертации), либо уехало, но не подтвердилось (уровень транспорта и платформенной нумерации сообщений). Это три разных места поиска.

### 1.2. Конвейер из четырёх стадий

Логически механизм — конвейер. Стадии слабо связаны и отлаживаются раздельно.

```
   ЗАПИСЬ ОБЪЕКТА
        │
        ▼
┌───────────────────┐
│ 1. РЕГИСТРАЦИЯ    │  Что изменилось и кому адресовано.
│                   │  Синхронно, в транзакции записи объекта.
│  ПРО + отборы     │  → таблица регистрации изменений плана обмена
└───────────────────┘
        │                       ...накапливается до сеанса обмена...
        ▼
┌───────────────────┐
│ 2. КОНВЕРТАЦИЯ    │  Внутренняя структура → нейтральный формат.
│                   │  КД3 (EnterpriseData/XDTO) или КД2 (XML-правила).
│  выгрузка         │  → тело сообщения обмена
└───────────────────┘
        │
        ▼
┌───────────────────┐
│ 3. ТРАНСПОРТ      │  Доставка сообщения корреспонденту.
│                   │  Файл / FTP / почта / COM / веб-сервис / внутр. публикация
│  отправка+приём   │  → файл или поток на той стороне
└───────────────────┘
        │
        ▼
┌───────────────────┐
│ 4. ЗАГРУЗКА       │  Формат → внутренняя структура получателя.
│                   │  Разрешение идентичности, запись, обработка проблем.
│  + идентификация  │  → объекты в базе + проблемы в мониторе
└───────────────────┘
```

**Ключевое свойство: стадии 1 и 2–4 разнесены во времени.** Регистрация происходит синхронно при записи объекта и обязана быть быстрой — она внутри пользовательской транзакции. Остальное происходит потом, в фоне. Отсюда практическое правило: **тяжёлая логика в правилах регистрации напрямую бьёт по времени записи документов у пользователей.**

### 1.3. Слои кода

Механизм следует общим соглашениям БСП о слоях, но с оговоркой: центральный модуль их нарушает, совмещая все три.

| Слой | Назначение | Модули |
|---|---|---|
| **Клиент** | Формы, помощники, интерактив | `ОбменДаннымиКлиент`, `ОбменДаннымиГлобальный` |
| **Сервервызов** | Тонкая прослойка клиент → сервер | `ОбменДаннымиВызовСервера` |
| **Программный интерфейс** | Публичный контракт для прикладного кода | `ОбменДаннымиСервер`, область `ПрограммныйИнтерфейс` |
| **Переопределяемый** | Точки расширения конфигурации | `ОбменДаннымиПереопределяемый` |
| **Бизнес-логика** | Ядро: регистрация, конвертация, контроль | `ОбменДаннымиСобытия`, `ОбменДаннымиXDTOСервер`, `ОбменДаннымиКонтрольЗацикливания` |
| **Служебный** | Внутренняя реализация, контракта нет | `ОбменДаннымиСлужебный`, `ОбменДаннымиВнешнееСоединение`, `ОбменДаннымиОценкаПроизводительности` |
| **Кэш** | Повторно используемые значения | `ОбменДаннымиПовтИсп`, `ОбменДаннымиТрансляцияФорматаПовтИсп`, `ОбменДаннымиРегистрацияПовтИсп` |

⚠️ **`ОбменДаннымиСервер` — смешанный модуль.** 13 165 строк, 282 экспортных метода, и в нём присутствуют **все три** области. Карта областей (проверена по коду):

```
9      #Область ПрограммныйИнтерфейс          ← публичный контракт
1039     #Область НастройкиПодключенияКВнешнейСистеме
1110     #Область СохранениеНастроекСинхронизацииДанных
1185     #Область ОбщиеНастройкиУзловИнформационныхБаз
1267     #Область ДляВызоваИзДругихПодсистем   ← для БСП, не для прикладного кода
1435     #Область УстаревшиеПроцедурыИФункции  ← НЕ ИСПОЛЬЗОВАТЬ
1650   #КонецОбласти
1722   #Область СлужебныйПрограммныйИнтерфейс  ← внутренний контракт БСП
5837   #Область СлужебныеПроцедурыИФункции     ← частная реализация
```

**Правило работы с этим модулем:** экспортность метода ничего не гарантирует. Перед вызовом определите, в какой области он лежит. Публичным контрактом является только область `ПрограммныйИнтерфейс` до строки 1435, за вычетом устаревшего блока.

### 1.4. Как слои взаимодействуют

Три существенных момента.

**Обратный вызов через переопределяемый модуль.** Конфигурация не вызывает БСП напрямую при регистрации — наоборот, БСП вызывает конфигурацию через `ОбменДаннымиПереопределяемый`. Инверсия управления: механизм — фреймворк, конфигурация — плагин к нему.

**Кэширование как несущий элемент, а не оптимизация.** Метаданные планов обмена, состав ПРО и таблицы трансляции формата читаются на каждый объект в цикле выгрузки. Без `ПовтИсп`-слоя обмен неработоспособен на реальных объёмах. Показателен `ОбменДаннымиТрансляцияФорматаПовтИсп`: 2 954 строки и **ровно один** экспортный метод — весь модуль есть одна большая кэшируемая функция.

**Симметрия сторон.** Обе базы исполняют один и тот же код: каждая и отправляет, и принимает. Это не «главный и подчинённый» (исключение — РИБ). Отсюда требование: любая доработка регистрации или конвертации должна быть **согласованно внесена в обе базы**, иначе стороны разойдутся в понимании формата.

## 3. Модель данных

### 3.1. Три контура хранения

Объекты подсистемы (~180 в составе) распадаются на три группы по назначению и жизненному циклу:

| Контур | Что хранит | Жизненный цикл |
|---|---|---|
| **Идентичность** | Связь «наш объект ↔ объект корреспондента» | Вечный. Потеря = дубли |
| **Настройки** | Узлы, транспорт, отборы, версии формата | Долгоживущий, меняется при перенастройке |
| **Оперативный** | Состояния, проблемы, сообщения, архив | Короткий, чистится регламентом |

Различие критично при обслуживании: оперативный контур можно чистить, **контур идентичности — нельзя ни при каких обстоятельствах.**

### 3.2. Контур идентичности

| Объект | Роль |
|---|---|
| `РС.СоответствияОбъектовИнформационныхБаз` | Сопоставление для КД2: наш объект ↔ объект корреспондента |
| `РС.ПубличныеИдентификаторыСинхронизируемыхОбъектов` | Сопоставление для КД3: публичный UUID объекта в контуре обмена |
| `РС.ПсевдонимыПредопределенныхУзлов` | Сопоставление предопределённых узлов между базами |
| `РС.КонтурСинхронизации` | Идентификация контура синхронизации |

⚠️ Два регистра сопоставления существуют параллельно, потому что параллельно живут два поколения конвертации. Какой из них задействован — определяется тем, на КД2 или КД3 построен конкретный план обмена. При разборе проблем с дублями смотреть надо в тот, что соответствует вашему плану обмена.

### 3.3. Контур настроек

| Объект | Роль |
|---|---|
| `Справочник.СценарииОбменовДанными` | Сценарий — набор шагов «узел + направление», привязывается к регламентному заданию |
| `Справочник.СеансыОбменовДанными` | Контекст конкретного запуска (длительные операции, оценка производительности) |
| `РС.ОбщиеНастройкиУзловИнформационныхБаз` | Ненастроечные атрибуты узла: описание, дата запрета загрузки |
| `РС.НастройкиОбменаДаннымиXDTO` | Согласованная версия формата EnterpriseData и поддерживаемый состав объектов |
| `РС.ПравилаДляОбменаДанными` | Загруженные правила конвертации и регистрации (типовые из макета либо внешние) |
| `РС.НастройкиАрхиваСообщенийОбменов` | Политика архивирования сообщений |
| `РС.ОбработчикиСобытийСинхронизацииДанных` | Реестр обработчиков от подсистем-подписчиков |

Транспортные настройки живут в дочерней подсистеме `ТранспортСообщенийОбмена`. В составе подсистемы присутствуют `РС.УдалитьНастройкиТранспортаОбмена` и `РС.УдалитьНастройкиТранспортаОбменаДанными` — префикс `Удалить` означает устаревшие объекты, оставленные для миграции. ⚠️ Не использовать в новом коде.

### 3.4. Оперативный контур

| Объект | Роль |
|---|---|
| `РС.СостоянияОбменовДанными` | Последняя **попытка** по узлу и направлению |
| `РС.СостоянияУспешныхОбменовДанными` | Последний **успех** по узлу и направлению |
| `РС.РезультатыОбменаДанными` | Зарегистрированные проблемы — источник данных монитора |
| `РС.СообщенияОбменаДанными` | Метаданные сообщений |
| `РС.АрхивСообщенийОбменов` | Архив тел сообщений для разбора инцидентов |
| `РС.ДанныеОбъектовДляРегистрацииВОбменах` | ⚠️ Предположительно — снимок реквизитов объекта до записи, чтобы ПРО могли сравнить «было/стало». Выведено из имени и контекста, тело не читалось |
| `РС.ОбъектыНезарегистрированныеПриЗацикливании` | Что контроль зацикливания намеренно не отправил обратно |
| `РС.ИзмененияОбщихДанныхУзлов` | Изменения общих данных узлов |

**Зачем состояния разделены на два регистра.** «Попытка» и «успех» — разные факты. После серии неудач нужно знать не когда последний раз пытались, а до какой точки данные реально доехали. Одним регистром это не выражается.

### 3.5. Классификаторы и параметры

**Перечисления:** `ВидыТранспортаСообщенийОбмена`, `ДействияПриОбмене`, `РезультатыВыполненияОбмена`, `ПриоритетыОбъектовОбмена`, `ТипыПроблемОбменаДанными`, `РежимыВыгрузкиОбъектовОбмена`, `ВидыПравилДляОбменаДанными`, `ИсточникиПравилДляОбменаДанными`.

**Константы:** `ИспользоватьСинхронизациюДанных`, `ИспользоватьСинхронизациюДанныхВЛокальномРежиме`, `ПрефиксУзлаРаспределеннойИнформационнойБазы`, `КоличествоЭлементовВТранзакцииЗагрузкиДанных`, `ЗагрузитьСообщениеОбменаДанными`, `СообщениеОбменаДаннымиИзГлавногоУзла`, `ДанныеДляОтложенногоОбновления`, `ЭтоАвтономноеРабочееМесто`, `НастройкаПодчиненногоУзлаРИБЗавершена`, `КаталогСообщенийОбменаДаннымиДляWindows` / `...ДляLinux`.

**Параметры сеанса:** `ПравилаРегистрацииОбъектов`, `ПриоритетныеДанныеОбмена`, `ПаролиСинхронизацииДанных`, `ПараметрыСеансаСинхронизацииДанных`, `РежимЗагрузкиСообщенияОбменаДаннымиПередЗапуском`.

⚠️ `ПараметрСеанса.ПравилаРегистрацииОбъектов` — горячая точка: ПРО читаются из него на каждую запись объекта.

**Функциональные опции:** `ИспользоватьСинхронизациюДанных`, `ИспользоватьСинхронизациюДанныхВЛокальномРежиме`, `ПрефиксИнформационнойБазы`, `РаботаВАвтономномРежиме`.

**XDTO-пакеты:** `EnterpriseData_1_2_3` … `EnterpriseData_1_17_3` — полный ряд версий формата; плюс `ExchangeMessage`, `EnterpriseDataExchange_1_0_1_1`.

**Веб-сервисы:** `EnterpriseDataExchange_1_0_1_1`, `EnterpriseDataUpload_1_0_1_1`.

**Роль:** `ВыполнениеСинхронизацииДанных` — намеренно отделена от администрирования, чтобы сервисному пользователю обмена не выдавать полные права.

### 3.6. Схема связей

```
Справочник.СценарииОбменовДанными
        │ шаги: узел + направление
        ▼
   УЗЕЛ ПЛАНА ОБМЕНА  ◄── отборы определяют состав данных
        │
        ├──► РС.ОбщиеНастройкиУзловИнформационныхБаз   (атрибуты узла)
        ├──► настройки транспорта      (подсистема ТранспортСообщенийОбмена)
        ├──► РС.НастройкиОбменаДаннымиXDTO             (версия формата)
        │
        ├──► таблица регистрации изменений             (платформа!)
        │
        ├──► РС.СостоянияОбменовДанными                (попытка)
        ├──► РС.СостоянияУспешныхОбменовДанными        (успех)
        ├──► РС.РезультатыОбменаДанными                (проблемы → монитор)
        └──► РС.СообщенияОбменаДанными ──► РС.АрхивСообщенийОбменов

   ОБЪЕКТ ИБ  ◄──► РС.СоответствияОбъектовИнформационныхБаз          (КД2)
              ◄──► РС.ПубличныеИдентификаторыСинхронизируемыхОбъектов (КД3)
```

**Узел — центр модели.** Почти всё привязано к нему. Отсюда практическое следствие: удаление узла затрагивает множество таблиц — для этого существуют подписки `ПередУдалениемПланаОбмена` и `ОчиститьСсылкиНаУзелИнформационнойБазы`.

**Таблица регистрации изменений принадлежит платформе,** а не БСП. В составе подсистемы её нет и быть не может. При отладке «почему объект не уехал» смотреть надо именно туда — через выборку изменений по узлу.

## 5. Жизненный цикл

Типовой сценарий: **двусторонний обмен двух баз, формат EnterpriseData (КД3), транспорт — файловый каталог, запуск по расписанию.**

### Фаза A. Настройка узла (однократно)

**A1. Помощник настройки.** `Обработка.ПомощникСозданияОбменаДанными`. Создаётся узел плана обмена.

**A2. Транспорт.** Записываются настройки подключения (подсистема `ТранспортСообщенийОбмена`).

**A3. Общие настройки.** `РС.ОбщиеНастройкиУзловИнформационныхБаз` — описание, дата запрета загрузки.

**A4. Согласование формата.** Стороны обмениваются списками поддерживаемых версий EnterpriseData, выбирается максимальная общая → `РС.НастройкиОбменаДаннымиXDTO`. Сюда же попадает состав поддерживаемых объектов.

**A5. Сопоставление.** `Обработка.СопоставлениеОбъектовИнформационныхБаз` → заполнение контура идентичности.
⚠️ **Пропуск этого шага при непустых базах гарантирует дубли всех справочников.** Единственный шаг фазы, который нельзя переиграть без ручной чистки.

**A6. Начальная выгрузка.** `ЗарегистрироватьДанныеДляНачальнойВыгрузки(Узел)` — в очередь ставится весь массив под отборами, не изменения.

**A7. Завершение.** `ЗавершитьНастройкуСинхронизацииДанных(УзелОбмена)`, включение `РЗ.СинхронизацияДанных`. Далее `НастройкаСинхронизацииЗавершена(УзелОбмена)` возвращает Истина.

### Фаза B. Регистрация (синхронно, при каждой записи)

Происходит **внутри транзакции записи объекта**, в контексте пользовательского сеанса.

```
Запись объекта
   │
   ├─ B1. Срабатывает МеханизмРегистрацииОбъектовПередЗаписью* (по типу объекта)
   │
   ├─ B2. Чтение ПРО из ПараметрСеанса.ПравилаРегистрацииОбъектов
   │
   ├─ B3. АвтоРегистрацияРазрешена(ОбъектМетаданных, ИмяПланаОбмена)?
   │        └─ Нет → выход
   │
   ├─ B4. ОпределитьПолучателей(Объект, ИмяПланаОбмена) → массив узлов
   │        применяются отборы узлов и условия ПРО
   │
   ├─ B5. Сравнение «было/стало»
   │        ⚠️ предположительно через РС.ДанныеОбъектовДляРегистрацииВОбменах
   │        вышел из отбора → регистрируется удаление у получателя
   │
   └─ B6. Запись в таблицу регистрации изменений (платформа)
```

**Требование к производительности.** Стадия внутри пользовательской транзакции. Тяжёлые ПРО — прямой рост времени проведения документов. При жалобах «документы стали долго проводиться после настройки обмена» проверять надо в первую очередь сюда.

### Фаза C. Сеанс обмена (асинхронно, по расписанию)

```
РЗ.СинхронизацияДанных
   │
   ▼
ВыполнитьОбменДаннымиПоРегламентномуЗаданию(КодСценария)          :8835
   │
   ▼
ВыполнитьОбменДаннымиПоСценариюОбменаДанными(Отказ, Настройка)    :8735
   │  по шагам сценария
   ▼
ВыполнитьОбменДаннымиДляУзлаИнформационнойБазы(Узел, Параметры, Отказ)  :8906
   │
   ├──────── C1. ВЫГРУЗКА ────────────────────────────────┐
   │  • выборка изменений по узлу (платформа)             │
   │  • конвертация через ОбменДаннымиXDTOСервер          │
   │  • формирование сообщения обмена, нумерация          │
   │  • запись файла в каталог транспорта                 │
   │  • ⚠️ снятие регистрации ПОСЛЕ подтверждения приёма  │
   │  • фиксация состояний                                │
   └───────────────────────────────────────────────────────┘
   │
   ├──────── C2. ЗАГРУЗКА ─────────────────────────────────┐
   │  • чтение файла корреспондента                        │
   │  • для каждого объекта: поиск в контуре идентичности   │
   │      найден    → обновление                            │
   │      не найден → создание + регистрация идентификатора │
   │  • порционные транзакции                               │
   │      (КоличествоЭлементовВТранзакцииЗагрузкиДанных)    │
   │  • контроль зацикливания                               │
   │  • проблемные объекты → РС.РезультатыОбменаДанными     │
   └────────────────────────────────────────────────────────┘
   │
   ▼
C3. Фиксация: СостоянияОбменовДанными + СостоянияУспешныхОбменовДанными
```

⚠️ Шаги внутри C1 и C2 восстановлены по составу объектов и именам методов; тела `Обработка.ВыполнениеОбменаДанными` и `ОбменДаннымиXDTOСервер` не читались. Точный момент снятия регистрации и фиксации состояний проверять по коду.

**Три свойства фазы, которые важно понимать:**

1. **Снятие регистрации отложено до подтверждения.** Обрыв связи посередине не теряет данные — они уедут следующим сеансом. Это же означает, что повторная отправка одного и того же объекта — штатная ситуация, а не ошибка.
2. **Загрузка порционная.** Размер порции — рычаг «скорость против длительности блокировок».
3. **Проблема на объекте не останавливает сеанс.** Объект откладывается, обмен продолжается.

### Фаза D. Разбор проблем

```
Проблемный объект
   │
   ├─ D1. Запись в РС.РезультатыОбменаДанными
   │        тип из Перечисление.ТипыПроблемОбменаДанными
   │
   ├─ D2. Счётчик: КоличествоНерассмотренныхПроблем(Узлы)   :1520
   │
   ├─ D3. Разбор пользователем в мониторе проблем
   │
   └─ D4. Автоснятие: подписки ПроверитьУстранениеПроблемыДокумента
                              ПроверитьУстранениеПроблемыОбъекта
```

Автоснятие — существенная деталь: устранив причину (например, открыв период), пользователь не должен вручную закрывать проблему. Подписка отследит запись объекта и снимет пометку.

### Фаза E. Обслуживание

`РЗ.УдалениеНеактуальнойИнформацииСинхронизации` → `УдалитьНеактуальныеСообщенияОбмена`. Чистит оперативный контур по политике из `РС.НастройкиАрхиваСообщенийОбменов`.
⚠️ Контур идентичности не трогать никогда.

### 6.4. Практические следствия

**Подсистема несущая, а не периферийная.** 103 файла-потребителя. Изменения в её публичном контракте задевают широкий круг кода — отсюда и живучесть области `УстаревшиеПроцедурыИФункции`: БСП не может просто удалить методы.

**Двусторонняя связь с обновлением ИБ.** `ОбменДаннымиСервер` ↔ `ОбновлениеИнформационнойБазы` ссылаются друг на друга. Причина: обновление конфигурации в РИБ должно докатиться до подчинённых узлов, а обмен должен корректно вести себя во время обновления. ⚠️ Это самое хрупкое место при доработках — проверять обновление на конфигурации с настроенным РИБ.

**Автономное рабочее место — надстройка над обменом.** `АвтономнаяРаботаСлужебный`, `Константа.ЭтоАвтономноеРабочееМесто`, `ФункциональнаяОпция.РаботаВАвтономномРежиме`. Ломая обмен, ломаете и АРМ.

**Префиксация связана напрямую.** `ПрефиксацияОбъектовСобытия` — потребитель. Префикс ИБ обеспечивает уникальность кодов и номеров между узлами; менять его на работающем обмене нельзя.

**Модель сервиса — отдельная ветка поведения.** Целое семейство `СообщенияОбменаДанными*` и `ОбменДаннымиВМоделиСервиса*`. При доработке под коробочную поставку легко не заметить, что сломали облачный сценарий.

## Уверенность в изложенном

### Уверен

Архитектурные принципы. Стабильны от версии к версии БСП, на них можно опираться при проектировании.

1. **Разделение платформа / БСП.** Таблица регистрации изменений, сообщения обмена, нумерация и подтверждение приёма — платформенные. БСП строит поверх оркестратор, транспорт, конвертацию и наблюдаемость.

2. **Конвейер из четырёх стадий** (регистрация → конвертация → транспорт → загрузка) со слабой связанностью и раздельной отладкой.

3. **Разнесение регистрации и обмена во времени.** Регистрация синхронна и внутри пользовательской транзакции; остальное асинхронно. Отсюда требование лёгкости ПРО.

4. **Декларативность регистрации.** Правила вынесены из кода в ПРО.

5. **Нейтральный формат обмена.** Данные едут не в структуре отправителя, а в согласованном формате с версионированием. Обе базы переводят на свой язык. Именно это позволяет обмениваться конфигурациям разной структуры.

6. **Два поколения конвертации сосуществуют:** КД2 (XML-правила) и КД3 (EnterpriseData/XDTO). В новых задачах — только КД3.

7. **Контур идентичности критичен и вечен.** Без сопоставления объектов обмен создаёт дубли. Этот контур не чистится никогда.

8. **Разделение «попытка» и «успех»** в состояниях обменов — разные факты, требующие разного хранения.

9. **Модель «проблемы вместо падения».** Сбой на объекте регистрируется и откладывается, обмен продолжается. Осознанное проектное решение, без которого механизм неработоспособен на реальных объёмах.

10. **Снятие регистрации только после подтверждения приёма.** Гарантия недоставки-без-потери; следствие — повторная отправка объекта штатна.

11. **Расширение через переопределяемый модуль**, инверсия управления: БСП — фреймворк, конфигурация — плагин.

12. **Кэширование — несущий элемент**, а не оптимизация. Без `ПовтИсп`-слоя обмен нежизнеспособен.

13. **Симметрия сторон:** обе базы исполняют один код; доработки вносятся согласованно в обе.

14. **Слоевые соглашения БСП:** суффиксы `Клиент` / `ВызовСервера` / `Служебный` / `ПовтИсп` / `Переопределяемый`; области `ПрограммныйИнтерфейс` / `СлужебныйПрограммныйИнтерфейс` / `СлужебныеПроцедурыИФункции`.

15. **Роль префикса ИБ** — уникализация кодов и номеров между узлами.

### Требует проверки

Проверено по этому репозиторию, но подлежит сверке с вашим конфигуратором — эти вещи меняются между версиями БСП. Порядок соответствует приоритету проверки.

**1. Точка входа регистрации прикладных объектов — проверять первой.**
Утверждается, что регистрация идёт через вызовы `МеханизмРегистрацииОбъектовПередЗаписью*` из **модулей планов обмена**, а не через подписки БСП. Подписки `ВключитьИспользованиеПланаОбмена` / `ОтключитьИспользованиеПланаОбмена` проверены по XML (`Event=BeforeWrite`, пустой `Source`) — но они про активность самого плана обмена, а не про регистрацию прикладных объектов. **Как именно УТ 11.5 подключает механизм к своим документам — не проверялось.** Смотреть модуль конкретного плана обмена.

**2. Состав `ПараметрыОбмена` и `ДополнительныеПараметры`.**
У `ВыполнитьОбменДаннымиДляУзлаИнформационнойБазы` (`:8906`) — главной точки входа — состав структур по сигнатуре не раскрывается. Читать заголовочный комментарий на месте перед первым вызовом.

**3. Сигнатуры и номера строк раздела 4.**
Сверены с `src/CommonModules/*/Ext/Module.bsl` этого репозитория. Номера строк действительны только для этой версии; состав необязательных параметров БСП правит между релизами.

**4. Внутренности фазы C (выгрузка и загрузка).**
Восстановлены по составу объектов и именам методов. Тела `Обработка.ВыполнениеОбменаДанными` и `ОбменДаннымиXDTOСервер` не читались. Проверять: точный момент снятия регистрации относительно подтверждения приёма, момент фиксации состояний, порядок обработки порций при частичном сбое.

**5. Выбор версии WS-прокси.**
Шесть версий: `ПолучитьWSПрокси`, `_2_0_1_6`, `_2_1_1_7`, `_3_0_1_1`, `_3_0_2_1`, `_3_0_2_2`. Логика выбора по версии корреспондента не разбиралась.

**6. Назначение `РС.ДанныеОбъектовДляРегистрацииВОбменах`.**
Трактовка «снимок реквизитов до записи для сравнения было/стало в ПРО» выведена из имени и контекста. Тело регистра и обращения к нему не читались. Влияет на понимание шага B5.

**7. Границы областей `ОбменДаннымиСервер`.**
Номера строк (`ПрограммныйИнтерфейс` с 9, `УстаревшиеПроцедурыИФункции` 1435–1650, `СлужебныйПрограммныйИнтерфейс` с 1722, `СлужебныеПроцедурыИФункции` с 5837) действительны для этой версии. Перед вызовом любого метода проверять принадлежность области заново.

**8. Актуальная версия формата EnterpriseData.**
В конфигурации пакеты до `EnterpriseData_1_17_3`, но фактически согласованная версия лежит в `РС.НастройкиОбменаДаннымиXDTO` и может быть существенно ниже. Не ориентироваться на состав XDTO-пакетов.

**9. Обработчики обновления ИБ.**
Связка `ОбновлениеИнформационнойБазыБСД` + `ОбработатьДанныеДляОбновленияВПодчиненномУзле` собрана по составу подсистемы и именам; тела обработчиков не читались. Важно, поскольку это самое хрупкое место (см. 6.4).

**10. Числовые оценки зависимостей раздела 6.**
Получены подсчётом вхождений `ИмяМодуля.` по файлам. Это оценка связанности, а не точный анализ вызовов: в число попадают комментарии и строковые литералы. Порядок величин достоверен, точные значения — нет.

**11. Устаревшие объекты.**
`РС.УдалитьНастройкиТранспортаОбмена`, `РС.УдалитьНастройкиТранспортаОбменаДанными`, `РС.УдалитьРезультатыОбменаДанными` — префикс `Удалить` указывает на объекты для миграции. Проверить, что в вашей версии они действительно не используются, прежде чем на них опираться.

## Практические ориентиры

Короткая шпаргалка для типовых ситуаций.

| Ситуация | Где искать |
|---|---|
| Объект не уехал к корреспонденту | По стадиям: (1) есть ли запись в таблице регистрации изменений — платформа; (2) ПРО и отборы узла; (3) не отфильтрован ли при выгрузке; (4) дошло ли сообщение — транспорт |
| Появились дубли справочников | Контур идентичности. Скорее всего пропущен шаг A5 при настройке |
| Документы стали долго проводиться | Фаза B — ПРО внутри пользовательской транзакции |
| Объекты копятся в мониторе проблем | `РС.РезультатыОбменаДанными`, тип проблемы. Частая причина — `ДатыЗапретаИзменения` |
| Обмен идёт долго | Размер транзакции загрузки; `ОбменДаннымиОценкаПроизводительности`; объём начальной выгрузки |
| Данные ходят по кругу | `ОбменДаннымиКонтрольЗацикливания`, `РС.ОбъектыНезарегистрированныеПриЗацикливании` |
| Сломалось после обновления конфигурации | Двусторонняя связь с `ОбновлениеИнформационнойБазы`; проверять на конфигурации с настроенным РИБ |
| Работает локально, не работает в сервисе | `РаботаВМоделиСервиса` — 19 точек соприкосновения, отдельная ветка поведения |
