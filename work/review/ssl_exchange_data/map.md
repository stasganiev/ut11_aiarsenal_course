# Карта механизма: стандартная подсистема «Обмен данными» (БСП 3.1.10)

> **Назначение документа.** Навигационная карта незнакомого механизма для разработчика: что это, из чего состоит, как работает. Не документация и не руководство по реализации.
>
> **Источник.** Состав подсистемы — `src/Subsystems/СтандартныеПодсистемы/Subsystems/ОбменДанными.xml`. Модули, сигнатуры и номера строк — `src/CommonModules/*/Ext/Module.bsl` конфигурации УТ 11.5 в этом репозитории.
>
> **Статус проверки.** Всё, что ниже, разделено на два списка в конце документа: [Уверен](#уверен) и [Требует проверки](#требует-проверки). Второй список — приоритет для сверки с конфигуратором.
>
> **Платформа / конфигурация.** 1С:Предприятие 8.3.27, УТ 11.5 на поддержке, БСП 3.1.10.

---

## 1. Назначение

Механизм решает задачу **двусторонней синхронизации данных между информационными базами** — типовыми, доработанными и внешними системами. Боль, которую он закрывает: до БСП каждая конфигурация изобретала свой обмен — свои правила регистрации, свой транспорт, свою обработку коллизий, свой мониторинг. Разработчику приходилось писать всё от нуля и потом это поддерживать.

БСП вынесла в общий слой всё, что не зависит от прикладной специфики: **регистрацию изменений** (кто, что и кому должен отправить), **транспорт** (файл, FTP, email, COM, web-сервис, внутренняя публикация), **конвертацию** (XML-правила КД2 и XDTO/EnterpriseData КД3), **мониторинг и разбор проблем**. Прикладной разработчик описывает только план обмена и правила, а весь оркестратор получает готовым.

## 2. Ключевые объекты

Подсистема очень крупная (в `Content` ~180 объектов), поэтому ниже — только несущий каркас.

### Справочники

| Объект | Что хранит |
|---|---|
| `Справочник.СценарииОбменовДанными` | Сценарий = именованный набор шагов «с каким узлом и в каком направлении обмениваться», привязывается к регламентному заданию |
| `Справочник.СеансыОбменовДанными` | Сеансы обменов — контекст конкретного запуска (для длительных операций и оценки производительности) |

### Регистры сведений

| Объект | Что хранит |
|---|---|
| `РС.СоответствияОбъектовИнформационныхБаз` | Ядро сопоставления: связка «наш объект ↔ объект корреспондента». Без него обмен создаёт дубли |
| `РС.ПубличныеИдентификаторыСинхронизируемыхОбъектов` | То же для XDTO/EnterpriseData — публичный UUID объекта в контуре обмена |
| `РС.СостоянияОбменовДанными` / `РС.СостоянияУспешныхОбменовДанными` | Последняя попытка и последний **успех** по узлу+направлению. Разделены, чтобы после ошибки помнить, до какой точки данные реально доехали |
| `РС.РезультатыОбменаДанными` | Зарегистрированные проблемы обмена (непринятое по дате запрета, коллизии, ошибки объектов) — питает «Монитор проблем» |
| `РС.ОбщиеНастройкиУзловИнформационныхБаз` | Общие (не транспортные) настройки по узлу: описание, дата запрета загрузки и т.п. |
| `РС.НастройкиОбменаДаннымиXDTO` | Согласованная с корреспондентом версия формата EnterpriseData и поддерживаемые объекты |
| `РС.СообщенияОбменаДанными` / `РС.АрхивСообщенийОбменов` / `РС.НастройкиАрхиваСообщенийОбменов` | Метаданные сообщений и архив для разбора инцидентов |
| `РС.ПравилаДляОбменаДанными` | Загруженные правила конвертации/регистрации (типовые из макета либо внешние) |
| `РС.ДанныеОбъектовДляРегистрацииВОбменах` | Кэш значений реквизитов объекта **до** записи — чтобы ПРО могли сравнить «было/стало» |
| `РС.ОбъектыНезарегистрированныеПриЗацикливании` | Что механизм контроля зацикливания намеренно не отправил обратно |
| `РС.ИзмененияОбщихДанныхУзлов`, `РС.ПсевдонимыПредопределенныхУзлов`, `РС.КонтурСинхронизации` | Служебные: изменения общих данных, сопоставление предопределённых узлов, идентификация контура |
| `РС.ОбработчикиСобытийСинхронизацииДанных` | Реестр обработчиков событий синхронизации из подсистем-подписчиков |

## 4. Точки входа

Конкретные места, откуда механизм стартует.

### 4.1. При записи / проведении объекта — регистрация к отправке

Не через подписки БСП, а через **обработчики плана обмена**: в модуле плана обмена `ПриОтправкеДанныхПодписчику` / `ОбработкаПолученияДанныхДляПодчиненного`, а в модулях объектов — вызов `ОбменДаннымиСобытия.МеханизмРегистрацииОбъектовПередЗаписью(...)` и варианты:

- `МеханизмРегистрацииОбъектовПередЗаписьюДокумента(ИмяПланаОбмена, Источник, Отказ, РежимЗаписи, РежимПроведения)`
- `МеханизмРегистрацииОбъектовПередЗаписьюРегистра(ИмяПланаОбмена, Источник, Отказ, Замещение)`
- `МеханизмРегистрацииОбъектовПередЗаписьюКонстанты(ИмяПланаОбмена, Источник, Отказ)`
- `МеханизмРегистрацииОбъектовПередУдалением(ИмяПланаОбмена, Источник, Отказ)`

Именно здесь применяются ПРО и заполняется таблица регистрации.

### 4.2. Из регламентного задания

`РЗ.СинхронизацияДанных` → `ОбменДаннымиСервер.ВыполнитьОбменДаннымиПоРегламентномуЗаданию(КодСценарияОбмена)`. Задание в поставке выключено (`Use=false`), включается при настройке синхронизации.

### 4.3. Из формы / интерактивно

`ОбщаяКоманда.Синхронизировать`, `ОбщаяКоманда.СинхронизироватьСДополнительнымиПараметрами`, `ОбщаяКоманда.НастройкиСинхронизацииДанных` → `ОбменДаннымиКлиент.ОткрытьПанельСинхронизацииДанных(...)` / `ОбменДаннымиКлиент.ОткрытьПомощникНастройкиОбменаДанными(...)`, далее `Обработка.ПомощникИнтерактивногоОбменаДанными`.

### 4.4. При старте сеанса

`ОбменДаннымиКлиент.ПередНачаломРаботыСистемы` / `ПриНачалеРаботыСистемы` / `ПослеНачалаРаботыСистемы`. Подчинённый узел РИБ здесь получает и применяет сообщение из главного узла — см. `Константа.СообщениеОбменаДаннымиИзГлавногоУзла` и `ОбменДаннымиСервер.ЗагрузитьПриоритетныеДанныеВПодчиненныйУзелРИБ`.

### 4.5. При обновлении ИБ

`ОбновлениеИнформационнойБазыБСД` + `ОбменДаннымиСервер.ОбработатьДанныеДляОбновленияВПодчиненномУзле(...)` — передача данных отложенного обновления в подчинённые узлы РИБ (`Константа.ДанныеДляОтложенногоОбновления`).

### 4.6. Извне — корреспондент обращается к нам

`WebService.EnterpriseDataExchange_1_0_1_1` / `WebService.EnterpriseDataUpload_1_0_1_1` → `ОбменДаннымиОперацииВебСервисов`; либо через COM → `ОбменДаннымиВнешнееСоединение`.

### 4.7. Подписки на события

Проверено по XML: `ВключитьИспользованиеПланаОбмена` / `ОтключитьИспользованиеПланаОбмена` (`Event=BeforeWrite`, пустой `Source`), `ЗарегистрироватьИзмененияОбщихДанныхУзлов`, `ЗарегистрироватьИзмененияФильтровОграниченияМиграцииДанных`, `ПроверитьИзменениеФильтровОграниченияМиграцииДанных`, `ПроверитьУстранениеПроблемыДокумента` / `ПроверитьУстранениеПроблемыОбъекта`, `ОчиститьСсылкиНаУзелИнформационнойБазы`, `ПередУдалениемПланаОбмена`, `ОтменитьОтправкуДанныхУзлаВРаспределеннойИнформационнойБазе`, `ОтключитьАвтоматическуюСинхронизациюДанных`, `ПроверитьВозможностьИзмененияНастроекОбменаДанными`.

## 6. Типовой сценарий

Самый частый случай — **регламентный двусторонний обмен двух баз через файловый каталог, формат EnterpriseData**.

**Шаг 1. Настройка (однократно).**
Пользователь запускает помощника (`Обработка.ПомощникСозданияОбменаДанными`). Создаётся узел плана обмена, пишутся транспортные настройки (каталог) и общие настройки (`РС.ОбщиеНастройкиУзловИнформационныхБаз`). Согласовывается версия формата с корреспондентом → `РС.НастройкиОбменаДаннымиXDTO`. По завершении вызывается `ЗавершитьНастройкуСинхронизацииДанных(УзелОбмена)`, включается `РЗ.СинхронизацияДанных`.

**Шаг 2. Начальное наполнение.**
`ЗарегистрироватьДанныеДляНачальнойВыгрузки(Узел)` ставит в очередь всё, что подпадает под отборы узла. При необходимости — ручное сопоставление через `Обработка.СопоставлениеОбъектовИнформационныхБаз` с записью в `РС.СоответствияОбъектовИнформационныхБаз`, чтобы не наплодить дубли.

**Шаг 3. Работа пользователей — регистрация «на лету».**
Каждая запись объекта проходит через `ОбменДаннымиСобытия.МеханизмРегистрацииОбъектовПередЗаписью*`. Механизм читает ПРО (`ПараметрСеанса.ПравилаРегистрацииОбъектов`), вычисляет получателей (`ОпределитьПолучателей`), сравнивает «было/стало» через `РС.ДанныеОбъектовДляРегистрацииВОбменах` и пишет запись в таблицу регистрации изменений плана обмена. Объект попал в отбор → регистрируется; вышел из отбора → регистрируется как удаление у получателя.

**Шаг 4. Срабатывает регламентное задание.**
`ВыполнитьОбменДаннымиПоРегламентномуЗаданию(КодСценария)` → `ВыполнитьОбменДаннымиПоСценариюОбменаДанными` → по шагам сценария `ВыполнитьОбменДаннымиДляУзлаИнформационнойБазы(Узел, ПараметрыОбмена, Отказ)`.

**Шаг 5. Выгрузка.**
`Обработка.ВыполнениеОбменаДанными` обходит регистрацию изменений, конвертирует объекты через `ОбменДаннымиXDTOСервер` в XML формата EnterpriseData, пишет файл в каталог. Успешно отправленное снимается с регистрации после подтверждения приёма номера сообщения. Пишутся `РС.СостоянияОбменовДанными` и `РС.СостоянияУспешныхОбменовДанными`.

**Шаг 6. Загрузка.**
Читается файл от корреспондента. Для каждого объекта по `РС.ПубличныеИдентификаторыСинхронизируемыхОбъектов` ищется наш объект: нашли — обновляем, нет — создаём и регистрируем идентификатор. Транзакции порциями (`Константа.КоличествоЭлементовВТранзакцииЗагрузкиДанных`). `ОбменДаннымиКонтрольЗацикливания` гасит отправку загруженного обратно источнику.

**Шаг 7. Проблемы, а не падение.**
Объект не прошёл (коллизия, дата запрета загрузки, ошибка проведения) → запись в `РС.РезультатыОбменаДанными` с типом из `Перечисление.ТипыПроблемОбменаДанными`. Обмен продолжается. Пользователь видит счётчик через `КоличествоНерассмотренныхПроблем()` и разбирает в мониторе проблем; после исправления подписки `ПроверитьУстранениеПроблемыДокумента` / `ПроверитьУстранениеПроблемыОбъекта` снимают проблему автоматически.

**Шаг 8. Уборка.**
`РЗ.УдалениеНеактуальнойИнформацииСинхронизации` → `УдалитьНеактуальныеСообщенияОбмена` чистит старые сообщения и архив по `РС.НастройкиАрхиваСообщенийОбменов`.

## Уверенность в изложенном

### Уверен

Базовая архитектура БСП, стабильная от версии к версии:

- **План обмена платформы** (регистрация изменений, узлы, отборы) — фундамент; БСП строит поверх него оркестратор и мониторинг.
- Трёхслойное разделение **«регистрация → транспорт → конвертация»** и две дочерние подсистемы `Регистрация` / `ТранспортСообщенийОбмена`.
- Два поколения конвертации живут параллельно: **КД2** (XML-правила, `УниверсальныйОбменДаннымиXML`) и **КД3** (XDTO/EnterpriseData). В новых задачах — только КД3.
- Роль **префикса ИБ**: уникализация кодов и номеров между узлами; без него неизбежны конфликты нумерации.
- Разделение `СостоянияОбменовДанными` / `СостоянияУспешныхОбменовДанными` — попытка ≠ успех.
- Идеология **«проблемы вместо падения»**: сбой на объекте регистрируется в `РезультатыОбменаДанными`, обмен идёт дальше.
- Расширение через `ОбменДаннымиПереопределяемый`, а не правкой модулей БСП.
- Слоевые соглашения БСП: суффиксы `Клиент` / `ВызовСервера` / `Служебный` / `ПовтИсп` / `Переопределяемый`; области `ПрограммныйИнтерфейс` / `СлужебныйПрограммныйИнтерфейс` / `СлужебныеПроцедурыИФункции`.

### Требует проверки

Разделы 2–5 взяты из `src/` этого репозитория, но сверять в конфигураторе в первую очередь нужно следующее.

1. **Сигнатуры из раздела 5.** Имена и номера строк сверены с `src/CommonModules/*/Ext/Module.bsl`, но состав необязательных параметров БСП правит между релизами. Особенно `ВыполнитьОбменДаннымиДляУзлаИнформационнойБазы` — что именно кладётся в `ПараметрыОбмена` и в `ДополнительныеПараметры`, по подписи не раскрыто; смотреть заголовочный комментарий на строке ~8906.

2. **Версия WS-прокси.** Присутствуют `_2_0_1_6`, `_2_1_1_7`, `_3_0_1_1`, `_3_0_2_1`, `_3_0_2_2`. Какую использовать — зависит от версии корреспондента; логика выбора не проверялась.

3. **Точка входа регистрации — самое важное для проверки.** Утверждается, что регистрация идёт через `ОбменДаннымиСобытия.МеханизмРегистрацииОбъектовПередЗаписью*`, вызываемые из **модулей планов обмена**, а не через подписки БСП. Подписки `ВключитьИспользованиеПланаОбмена` / `ОтключитьИспользованиеПланаОбмена` проверены — у них `Event=BeforeWrite` и пустой `Source`, но это про включение самого плана обмена, а не про регистрацию прикладных объектов. Как именно УТ 11.5 подключает механизм регистрации к своим документам — **смотреть модуль конкретного плана обмена**, это не проверялось.

4. **Шаги 5–7 типового сценария.** Восстановлены по составу объектов и именам функций, не по чтению тел `Обработка.ВыполнениеОбменаДанными` и `ОбменДаннымиXDTOСервер`. Порядок «снятие с регистрации после подтверждения номера сообщения» и точный момент фиксации состояний — проверить по коду.

5. **Слой `ОбменДаннымиСервер`.** Назван смешанным — реально содержит все три области (`ПрограммныйИнтерфейс` с 9, `СлужебныйПрограммныйИнтерфейс` с 1722, `СлужебныеПроцедурыИФункции` с 5837). Перед вызовом любой его функции проверять, в какой области она лежит; из `УстаревшиеПроцедурыИФункции` (1435–1650) не брать.

6. **`РС.ДанныеОбъектовДляРегистрацииВОбменах`.** Назначение («кэш реквизитов до записи для сравнения было/стало») выведено из имени и контекста ПРО, тело не читалось.

7. **Актуальная версия формата EnterpriseData.** В конфигурации пакеты до `EnterpriseData_1_17_3`, но фактически согласованная с корреспондентом версия лежит в `РС.НастройкиОбменаДаннымиXDTO` и может быть значительно ниже.

8. **Точка входа при обновлении ИБ.** Связка `ОбновлениеИнформационнойБазыБСД` + `ОбработатьДанныеДляОбновленияВПодчиненномУзле` собрана по составу подсистемы и именам; обработчики обновления не читались.
