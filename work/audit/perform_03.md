## П-01 · Запрос в цикле: `ЗаменитьРолиВПрофилях` → цикл по профилям → `ПолучитьОбъект` + `Записать` на каждую итерацию

**Где:**  
`УправлениеДоступомСлужебный`, строки 410–457 (функция `ЗаменитьРолиВПрофилях`)

**Что:**  
Сначала выполняется запрос, возвращающий список профилей / групп доступа. Затем в цикле по каждому элементу открывается транзакция, вызывается `ПолучитьОбъект()`, объект модифицируется и записывается. Итого: N транзакций + N чтений объекта + N записей объекта, где N — количество профилей/групп.

```
// строки 410–457 (упрощённо):
МассивПрофилей = Запрос.Выполнить()...  // 1 запрос
Для Каждого Профиль Из МассивПрофилей Цикл   // N итераций
    ПрофильОбъект = Профиль.ПолучитьОбъект()  // N чтений из БД
    ...
    ПрофильОбъект.Записать()                   // N записей → N подписок → рекурсия
КонецЦикла;

МассивГрупп = Запрос.Выполнить()...           // ещё 1 запрос
Для Каждого ГруппаДоступа Из МассивГрупп Цикл // M итераций
    ГруппаДоступаОбъект = ГруппаДоступа.ПолучитьОбъект()
    ГруппаДоступаОбъект.Записать()             // M записей
КонецЦикла;
```

**Масштаб:** ощутимо при 10+ профилях; при 50–100 профилях (типично для крупного УТ) — секунды ожидания при каждом обновлении конфигурации. Каждая запись группы дополнительно запускает цепочку подписок.

**Почему ревью одной функции не показывает:** глядя на цикл, он выглядит как «просто обход коллекции». Проблема в том, что `ПрофильОбъект.Записать()` внутри вызывает `ОбновитьРолиПользователейПриИзмененииГруппыДоступа` из ObjectModule (`ГруппыДоступа:169`), которая в свою очередь вызывает `УправлениеДоступомСлужебный.ОбновитьРолиПользователей` с новым пакетным запросом внутри — это три уровня вложенности, каждый в своём модуле.

**Уверенность:** высокая

## П-02 · Запрос в цикле: `ОбновитьРолиПользователейИБ` → `ЗаписатьПользователяПриОбновленииРолей` на каждого пользователя

**Где:**  
`УправлениеДоступомСлужебный`, строки 7207–7241 (`ОбновитьРолиПользователейИБ`) ← вызывается из `ОбновитьРолиПользователей` (строки 681–686)

**Что:**  
`ОбновитьРолиПользователей` формирует список всех пользователей, требующих обновления ролей, одним пакетным запросом (`ТекущиеСвойстваПользователей`, стр. 538), а затем передаёт соответствие в `ОбновитьРолиПользователейИБ`, которая открывает транзакцию и вызывает `ЗаписатьПользователяПриОбновленииРолей` для **каждого** пользователя по отдельности (стр. 7231–7240). Каждая такая запись — отдельный вызов `ПользователиСлужебный.ЗаписатьПользователяИнформационнойБазы`.

**Масштаб:** при изменении профиля группы, содержащей 200+ участников, выполняется 200+ последовательных транзакций. Это прямой путь к таймаутам при пакетном импорте пользователей или переназначении профиля «по организации».

**Почему ревью одной функции не показывает:** `ОбновитьРолиПользователей` выглядит оптимально — один большой запрос собирает данные. `ОбновитьРолиПользователейИБ` выглядит как «простое применение результата». Связь двух функций через соответствие скрывает, что бизнес-операция «обновить роли группы» разбивается на N транзакций на стыке этих двух функций.

**Уверенность:** высокая

## П-03 · Копирование пользователя между группами: `ВключитьОтключитьПрофильПользователя` → `ПолучитьОбъект` + `Записать` в цикле по группам

**Где:**  
`УправлениеДоступомСлужебный`, строки 2563–2574 (цикл при упрощённом интерфейсе) и строки 2563–2575 ← вызывается из `СкопироватьПользователяМеждуГруппами` (стр. 2546)

**Что:**  
Запрос на строках 2538–2543 возвращает список групп, в которых участвует исходный пользователь. Далее в цикле `Пока Выборка.Следующий() Цикл` для каждой группы:
- упрощённый интерфейс (стр. 2564): вызов `УправлениеДоступом.ВключитьОтключитьПрофильПользователя` → уходит в `УправлениеДоступомСлужебный.ВключитьОтключитьПрофильПользователяВГруппе` → `ПолучитьОбъект` + `Записать` (стр. 6410, 6428);
- расширенный интерфейс (стр. 2569–2574): `ПолучитьОбъект` прямо в цикле + `Записать`.

**Масштаб:** при копировании пользователя, у которого 10+ групп доступа (роли через несколько организаций в УТ), — 10+ транзакций синхронно в момент записи.

**Почему ревью одной функции не показывает:** в точке вызова (строка 2564) это выглядит как вызов публичного API. Внутри `ВключитьОтключитьПрофильПользователяВГруппе` — корректная атомарная операция с блокировкой. Проблема возникает именно на стыке: публичная функция вызывается N раз в цикле, не зная о контексте оптимизации снаружи.

**Уверенность:** высокая

## П-04 · Запрос в цикле при заполнении НаборыЗначенийДоступа: цикл по типам объектов → `ОбновитьНаборыЗначенийДоступа` на каждый объект

**Где:**  
`УправлениеДоступомСлужебный`, строки 3834–3858 (вложенный цикл `Пока Выборка.Следующий()` внутри `Для каждого ОписаниеТипа`)  
← вызывается из `ЗаполнитьДанныеДляОграниченияДоступа`

**Что:**  
Внешний цикл (стр. 3834) перебирает все типы объектов из ПовтИсп-кэша. Для каждого типа выполняется запрос (стр. 3851, помечен `@skip-check query-in-loop`), возвращающий объекты без наборов. Затем **внутренний цикл** (стр. 3854) по каждой найденной ссылке вызывает `ОбновитьНаборыЗначенийДоступа(Выборка.Ссылка, ...)` (стр. 3856), которая сама содержит запрос к `НаборыЗначенийДоступа` и запись.

Итог: K типов × M объектов каждого типа = K·M одиночных вызовов `ОбновитьНаборыЗначенийДоступа`.

**Масштаб:** критично при первичном заполнении базы с 100K+ объектов и 10+ видами доступа. Функция вызывается регламентным заданием `ЗаполнениеДанныхДляОграниченияДоступа`, которое ограничено 10 000 объектов за итерацию, — но даже это 10 000 последовательных вызовов.

**Почему ревью одной функции не показывает:** `ОбновитьНаборыЗначенийДоступа` — самодостаточная функция обновления одного объекта. Вызывающий код выглядит как «цикл порционной обработки». Но стоимость K·M=10 000 запросов видна только при совместном чтении обоих уровней цикла.

**Уверенность:** высокая (операция частично компенсируется ограничением `ПЕРВЫЕ 10000`, но одиночные записи в регистр остаются)

## П-05 · Повторное чтение одних данных: `ПараметрыОграничения` вычисляется на каждый вызов `ДоступРазрешен`

**Где:**  
`УправлениеДоступомСлужебный`, строка 10050: `ПараметрыОграничения = ПараметрыОграничения(ПолноеИмя, ИдентификаторТранзакции, ДляВнешнихПользователей)`  
← вызывается из `ДоступРазрешен` при каждой проверке доступа перед/при записи (подписки `ПроверитьДоступПередЗаписью`, `ПроверитьДоступПриЗаписи`)

**Что:**  
Функция `ПараметрыОграничения` строит текст RLS-запроса для конкретной таблицы (через вызовы `УправлениеДоступомСлужебныйПовтИсп.СинтаксисЯзыка`, парсер, разбор метаданных). При массовой записи документов одного типа (например, 500 заказов в пакетной обработке) эта функция вызывается 500 раз для одного и того же `ПолноеИмя`. Структура параметров идентична для одного типа объекта, но не кэшируется между вызовами `ДоступРазрешен`.

**Масштаб:** при пакетной обработке 500+ объектов одного типа в одном сеансе. Парсинг текста RLS-шаблона — нетривиальная операция (~5 000 строк парсера), выполняемая повторно.

**Почему ревью одной функции не показывает:** `ПараметрыОграничения` использует кэш `ПовтИсп` для `СинтаксисЯзыка` и некоторых метаданных (стр. 10452, 10491), поэтому изнутри выглядит оптимизированной. Но уровнем выше — на стыке «подписка → `ДоступРазрешен` → `ПараметрыОграничения`» — кэша готовой структуры `ПараметрыОграничения` по типу объекта нет.

**Уверенность:** средняя (требует профилировки — зависит от объёма парсинга в конкретной конфигурации)

## П-06 · Обход кэша: прямое чтение константы вместо ПовтИсп при частой проверке флага RLS

**Где:**  
`УправлениеДоступомСлужебный`, строки 771–805 (функция `ОграничиватьДоступНаУровнеЗаписейУниверсально`)  
vs.  
`УправлениеДоступомСлужебныйПовтИсп`, функция `КонстантаОграничиватьДоступНаУровнеЗаписейУниверсально`

**Что:**  
В `УправлениеДоступомСлужебный` есть локальная функция `ОграничиватьДоступНаУровнеЗаписейУниверсально` (не экспортная), которая на строках 771–805 обращается к `УправлениеДоступомСлужебныйПовтИсп.КонстантаОграничиватьДоступНаУровнеЗаписейУниверсально()` — это корректно. Однако в ObjectModule `ГруппыДоступа` (строка 182) и в нескольких других местах самого `УправлениеДоступомСлужебный` (строки 195, 3828, 3864) вызов идёт через `УправлениеДоступомСлужебный.ОграничиватьДоступНаУровнеЗаписейУниверсально()`, а не напрямую через `ПовтИсп`. Эта обёртка при определённых условиях (истёкшая проверка версии на стр. 789–798) читает константу заново из БД и инвалидирует кэш `ПовтИсп`.

**Масштаб:** при высокой частоте записи (сотни транзакций/мин) каждый вызов обёртки потенциально перечитывает константу. Незначительно само по себе, но суммируется при срабатывании всех подписок.

**Почему ревью одной функции не показывает:** `ОграничиватьДоступНаУровнеЗаписейУниверсально` в `Служебный` выглядит как «умный кэш с проверкой версии». ObjectModule `ГруппыДоступа` выглядит как «обычный вызов». Лишний слой индирекции виден только при сравнении двух модулей.

**Уверенность:** средняя

## П-07 · «Жадное» чтение объекта ради одного поля: `ПолучитьОбъект()` для проверки `ПометкаУдаления`

**Где:**  
`УправлениеДоступомСлужебный`, строка 5506:  
`ПрофильОбъект = Ссылка.ПолучитьОбъект()` → используется только `ПрофильОбъект.ПометкаУдаления = Истина`

`УправлениеДоступомСлужебный`, строки 5515–5530: цикл по `ГруппыПрофиля`:  
`ГруппаОбъект = СсылкаГруппы.ПолучитьОбъект()` → только `ГруппаОбъект.ПометкаУдаления = Истина` + `Записать()`

**Что:**  
В обоих случаях загружается полный объект справочника (со всеми ТЧ: `Пользователи`, `ВидыДоступа`, `ЗначенияДоступа`) ради установки одного булевого реквизита `ПометкаУдаления`. Для `ГруппыДоступа` с тысячами участников в ТЧ `Пользователи` это означает загрузку мегабайт данных per iteration.

**Масштаб:** при удалении профиля с 10+ связанными группами, каждая из которых содержит 1 000+ пользователей — критически медленная операция.

**Почему ревью одной функции не показывает:** строка 5506 — одиночный `ПолучитьОбъект` в теле условия, выглядит нормально. Строки 5515–5530 — цикл по «небольшому» списку групп. Проблема на стыке: вызывающий код не знает, сколько пользователей в ТЧ каждой группы, а вызываемая операция «пометить на удаление» не нуждается в этих данных совсем — достаточно точечного обновления реквизита через менеджер записи или прямой SQL-подобный запрос на обновление.

**Уверенность:** высокая

## П-08 · Разрыв пакетного запроса на границе модулей: `НаборыЗначенийДоступа` пишутся построчно вместо набором

**Где:**  
`УправлениеДоступомСлужебный`, строки 3939–3953 (цикл `Пока Выборка.Следующий()`):  
```bsl
Пока Выборка.Следующий() Цикл
    МенеджерЗаписи = РегистрыСведений.НаборыЗначенийДоступа.СоздатьМенеджерЗаписи();
    ...
    МенеджерЗаписи.Записать();   // ← N отдельных записей в регистр
КонецЦикла;
```

**Что:**  
После получения выборки из запроса (строка 3936) код записывает каждую строку в `НаборыЗначенийДоступа` отдельным вызовом `МенеджерЗаписи.Записать()`. Логически это одна пакетная операция «обновить кэш-реквизиты», но она разбита на N транзакций на границе «запрос → цикл → запись». Вызывающий `ЗаполнитьДанныхДляОграниченияДоступа` не знает о стоимости каждой записи.

**Масштаб:** при 10 000 строк выборки — 10 000 отдельных вызовов менеджера записи. Запись набором через `НаборЗаписей` снизила бы нагрузку на порядок.

**Почему ревью одной функции не показывает:** функция, содержащая цикл, уже помечена в одном месте `@skip-check query-in-loop`. Сам цикл записи выглядит как «стандартный паттерн». Только при взгляде на контекст вызова (регламентное задание обходит тысячи записей) становится ясно, что нужен `НаборЗаписей`.

**Уверенность:** высокая

## Приоритет исправления

1. **П-02, П-01** — синхронные потоки при записи групп доступа, прямо влияют на UX администраторов
2. **П-04, П-08** — регламентное задание: медленнее накапливается очередь, дольше «догоняет» изменения прав
3. **П-07** — потенциально блокирующая операция при удалении профиля с крупными группами
4. **П-03** — узкое место при миграции/клонировании пользователей
5. **П-05, П-06** — фоновый шум, требует профилировки перед принятием решения
