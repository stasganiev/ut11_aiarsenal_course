## E-01 · Утечка привилегированного режима — `РазрешенныеЗначенияДляДинамическогоСписка`

**Где:** `УправлениеДоступомСлужебный`, функция `РазрешенныеЗначенияДляДинамическогоСписка`, строки 127–333

**Что:** `УстановитьПривилегированныйРежим(Истина)` установлен на стр. 127; ни одного парного `Ложь` до `КонецФункции` на стр. 333. Из функции есть три точки выхода (`Возврат` на стр. 122, 303, 331) — во всех трёх режим не снимается.

**Сценарий срабатывания:** вызов `РазрешенныеЗначенияДляДинамическогоСписка()` из любого места, где пользователь не является администратором (форма динамического списка с RLS-ограничением). После возврата из функции весь последующий код текущего серверного вызова выполняется с поднятыми привилегиями — в том числе запись объектов, вызов других модулей.

**Почему тесты не ловят:** функция возвращает корректные данные. Привилегированный режим — сквозное состояние сеанса, не видное в логике самой функции. Unit-тесты проверяют результат, а не состояние режима после вызова.

**Уверенность: высокая**

## E-02 · Утечка привилегированного режима — `ПроверитьНаличиеПользователяИБВГруппеДоступаАдминистраторы`

**Где:** `УправлениеДоступомСлужебный`, процедура `ПроверитьНаличиеПользователяИБВГруппеДоступаАдминистраторы`, строки 3309–3338

**Что:** `УстановитьПривилегированныйРежим(Истина)` на стр. 3309, парного `Ложь` до `КонецПроцедуры` на стр. 3338 нет. Процедура экспортная, вызывается перед записью группы доступа «Администраторы».

**Сценарий срабатывания:** любая попытка записи группы доступа «Администраторы» с непустым списком пользователей. Код проверки записи пользователей ИБ — `ПользователиИнформационнойБазы.НайтиПоУникальномуИдентификатору` — работает корректно, однако вызывающий код ObjectModule `ГруппыДоступа` далее работает в привилегированном режиме неявно.

**Почему тесты не ловят:** проверка прав при записи выполняется успешно, результат не меняется. Побочный эффект (поднятый режим) проявляется только в сложных многоуровневых сценариях.

**Уверенность: высокая**

## E-03 · Утечка привилегированного режима — `ПриЗаполненииВсехПараметровРаботыРасширений`

**Где:** `УправлениеДоступомСлужебный`, процедура `ПриЗаполненииВсехПараметровРаботыРасширений`, строки 2284–2325

**Что:** Строки 2286–2287: `УстановитьОтключениеБезопасногоРежима(Истина)` и `УстановитьПривилегированныйРежим(Истина)`. На стр. 2296 — `Возврат` при раннем выходе (`НеобходимоОбновление()`). Парных `Ложь` нет ни перед `Возврат`, ни перед `КонецПроцедуры`.

**Сценарий срабатывания:** обновление параметров работы расширений в момент, когда `ПараметрыРаботыПрограммы.НеобходимоОбновление()` возвращает `Истина` (первый запуск после обновления конфигурации). Выход через ранний `Возврат` оставляет привилегированный режим активным.

**Почему тесты не ловят:** ранний выход — штатное поведение при определённом состоянии ИБ, а не ошибка. Состояние режима после возврата проверяется крайне редко.

**Уверенность: высокая**

## E-04 · Утечка привилегированного режима — группа функций `ЗаполнениеДанныхДляОграниченияДоступа`, `ЗапуститьОбновлениеДоступаНаУровнеЗаписей`, `ВыполнитьОбновлениеДоступаСпискаВФоне`

**Где:** `УправлениеДоступомСлужебный`, строки 3776, 12349, 15636 — три процедуры регламентных заданий

**Что:** каждая из трёх устанавливает `УстановитьПривилегированныйРежим(Истина)` в начале и не снимает явно. Это служебные точки входа для фоновых заданий, поэтому время жизни сеанса ограничено временем задания — утечка не распространяется на пользовательский сеанс.

**Сценарий срабатывания:** не является проблемой в штатном режиме фонового задания. Риск возникает, если один из этих методов вызывается напрямую из пользовательского кода (например, интерактивное заполнение данных через форму).

**Почему тесты не ловят:** в тестах задания запускаются в изолированных сеансах. Вызов из пользовательского контекста не тестируется.

**Уверенность: средняя** (требует проверки точек прямого вызова из пользовательского кода)

## E-05 · Молчаливое поглощение ошибки при неудаче блокировки — `ОбновитьКлючиДоступаКРегистрам` / `ОбновитьКлючиДоступаКОбъектам`

**Где:** `УправлениеДоступомСлужебный`, порционная обработка ключей доступа, строки 20586–20623 и 20696–20770

**Что:** В блоке `Исключение` (`ОтменитьТранзакцию`) стоит условный `ВызватьИсключение`:

```bsl
Исключение
    ОтменитьТранзакцию();
    Если БлокировкаУстановлена Тогда
        ВызватьИсключение;
    КонецЕсли;
КонецПопытки;
КоличествоОбработанных = 0;  // <- сброс счётчика, цикл продолжается
```

Если ошибка произошла **до** установки блокировки (`Блокировка.Заблокировать()`), исключение молча проглатывается, счётчик сбрасывается в 0, и цикл продолжает работу со следующей порцией. Ни логирования, ни уведомления.

**Сценарий срабатывания:** ошибка соединения с базой данных или прерывание фонового задания в момент попытки блокировки (до её фиксации в `БлокировкаУстановлена = Истина`). Часть ключей доступа не обновляется, но задание продолжает работу как будто всё в порядке. Пользователи получают устаревшие права без какого-либо предупреждения.

**Почему тесты не ловят:** сбой до установки блокировки — нестандартная ситуация (сетевой сбой, deadlock на уровне СУБД), которая не воспроизводится в обычных интеграционных тестах.

**Уверенность: высокая**

## E-06 · Использование `ИнформацияОбОшибке` вне блока Исключение

**Где:** `УправлениеДоступомСлужебный`, функция `РезультатПроверкиОграниченияДоступаСписка`, строки 25782–25786

**Что:** В блоке `Исключение` отсутствует вызов `ИнформацияОбОшибке()` — вместо этого используется переменная `ИнформацияОбОшибке`, которая могла быть установлена в предыдущем блоке Исключение этой же функции (стр. 25755):

```bsl
// Блок 1 — корректно:
Попытка
    ОбщийКонтекст = ...
Исключение
    ИнформацияОбОшибке = ИнформацияОбОшибке();  // стр. 25755
    Результат.ОшибкаОписанияОграничения = ...
КонецПопытки;

// Блок 2 — ОШИБКА: ИнформацияОбОшибке здесь — это переменная из блока 1:
Попытка
    ОписаниеОграничения = ...
Исключение
    Результат.ОшибкаОписанияОграничения = ОбработкаОшибок.ПодробноеПредставлениеОшибки(ИнформацияОбОшибке);  // стр. 25785
    // ИнформацияОбОшибке() — функция не вызвана! Используется переменная из блока 1.
КонецПопытки;
```

**Сценарий срабатывания:** второй блок Попытка падает после того, как первый блок уже перехватил ошибку. В `Результат.ОшибкаОписанияОграничения` попадает описание **предыдущей** ошибки, а не текущей. Диагностика вводит в заблуждение.

**Почему тесты не ловят:** функция возвращает структуру с текстом ошибки (не бросает исключение). Тесты проверяют факт наличия ошибки, а не точность её текста.

**Уверенность: высокая**

## E-07 · Молчаливое поглощение ошибки чтения хранилища значений

**Где:** `УправлениеДоступомСлужебный`, функция `ЗначениеИзХранилища`, строки 29697–29701

**Что:**

```bsl
Функция ЗначениеИзХранилища(ХранилищеЗначения)
    Попытка
        Значение = ХранилищеЗначения.Получить();
    Исключение
        Значение = Неопределено;  // ← ошибка проглочена
    КонецПопытки;
    Возврат Значение;
КонецФункции
```

Ошибка десериализации (битые данные, несовместимость версий) молча заменяется на `Неопределено`. Вызывающий код обязан проверить `Неопределено`, иначе происходит выполнение ветки «нет данных» там, где данные фактически повреждены.

**Сценарий срабатывания:** повреждение данных в `РегистрСведений.ПараметрыРаботыВерсийРасширений` (например, после неудачного обновления конфигурации с несовместимыми типами). Функция используется в `УстановитьВерсиюПараметров` и `СпискиСИзменениемВерсий` — оба обновляют RLS-параметры. При повреждённых данных параметры не обновляются молча, права пользователей застывают.

**Почему тесты не ловят:** в тестах хранилище содержит корректные данные. Битые данные — производственная ситуация.

**Уверенность: средняя** (умысел вероятен — защита от «старых» несовместимых версий; но отсутствие логирования делает инцидент невидимым)

## E-08 · Молчаливое поглощение ошибки записи расширения

**Где:** `УправлениеДоступомСлужебный`, процедура обработки расширений, строки 7262–7270

**Что:**

```bsl
// АПК:280-выкл - №499.3.4 Допустимо пропустить обработку исключения, так как
// это не останавливающая операция и будет выполнена успешно при очередном обновлении ролей.
// Запись расширения не является транзакционной операцией, поэтому не создает ошибок в транзакции.
Попытка
    Расширение.Записать();
Исключение
    // Обработка не требуется.
КонецПопытки;
```

**Оценка:** комментарий-обоснование присутствует, подавление намеренное. **Вероятно намеренно.** Однако отсутствует хотя бы запись в журнал регистрации — при повторяющемся сбое записи расширений диагностика невозможна без ручного просмотра фонового задания.

**Сценарий срабатывания:** ошибка записи расширения (блокировка, конфликт версий) повторяется несколько циклов подряд. Никакой диагностической информации не накапливается.

**Почему тесты не ловят:** ошибка записи в тестах не моделируется.

**Уверенность: средняя** (намерение явно указано в комментарии, но рекомендуется добавить хотя бы `ЗаписьЖурналаРегистрации` на уровне `Информация`)

## E-09 · Условное проглатывание исключения в расчёте параметров RLS

**Где:** `УправлениеДоступомСлужебный`, функция (расчёт параметров ограничения доступа), строки 25320–25335

**Что:**

```bsl
Попытка
    РассчитанныеПараметры = РассчитанныеПараметрыОграничения(ПолноеИмя, ОбщийКонтекст, ДействующиеПараметры);
Исключение
    Если ПовторныйВызов Тогда
        ВызватьИсключение;
    КонецЕсли;
    Попытка
        Значение = Константы.ОграничиватьДоступНаУровнеЗаписей.Получить();
    Исключение
        Значение = Неопределено;
    КонецПопытки;
    Если Значение = Неопределено Тогда
        ВызватьИсключение;
    КонецЕсли;
    ЕстьОшибка = Истина;  // ← исключение поглощено при Значение <> Неопределено
КонецПопытки;
```

При первом (не повторном) вызове, если константа читается успешно, ошибка расчёта RLS-параметров **поглощается** (`ЕстьОшибка = Истина`). Дальнейшая логика обрабатывает флаг, но исходный текст ошибки нигде не фиксируется.

**Сценарий срабатывания:** ошибка в `РассчитанныеПараметрыОграничения` (некорректный шаблон RLS, неожиданный тип данных) при первичном вызове. Система пытается продолжить без этого параметра. Пользователь получает либо слишком широкий, либо слишком узкий доступ; в журнале нет никакой записи о сбое расчёта.

**Почему тесты не ловят:** ошибка в парсере шаблонов RLS возникает только при определённых конфигурациях прав; в стандартных тестах шаблоны корректны.

**Уверенность: средняя**

## E-10 · Транзакция без гарантии отката при сбое до блокировки (два места)

**Где:** `УправлениеДоступомСлужебный`, строки 20586–20622 и 20696–20769 (порционная обработка ключей)

**Что:** Паттерн:

```bsl
БлокировкаУстановлена = Ложь;
НачатьТранзакцию();
Попытка
    Блокировка.Заблокировать();
    БлокировкаУстановлена = Истина;
    ...
    ЗафиксироватьТранзакцию();
Исключение
    ОтменитьТранзакцию();
    Если БлокировкаУстановлена Тогда
        ВызватьИсключение;
    КонецЕсли;
    // Иначе — транзакция отменена, исключение проглочено, цикл продолжен
КонецПопытки;
```

Транзакция корректно откатывается в обоих случаях. Проблема не в незакрытой транзакции, а в том, что при сбое до блокировки ошибка теряется (см. E-05). Сама транзакция закрыта.

**Оценка:** транзакционный аспект в порядке; это уточнение к E-05.

## Что проверено и не нашло проблем

- **Транзакции** (~40 блоков `НачатьТранзакцию`): паттерн `НачатьТранзакцию → Попытка → Зафиксировать → Исключение → Отменить → ВызватьИсключение` соблюдается стабильно во всём модуле. Незакрытых транзакций не обнаружено.
- **Деление на ноль**: явных делений переменной на переменную без проверки не выявлено (счётчики защищены через `Если Количество = 0`).
- **Пустые ссылки**: обращения к `Ссылка` внутри циклов по выборкам защищены через `ЗначениеЗаполнено` или предваряются запросами с `ГДЕ … ЕСТЬ NULL`.
- **NULL из запросов**: используется `.Выгрузить().ВыгрузитьКолонку()` вместо прямого `.Значение` — защита от NULL встроена в паттерн.
