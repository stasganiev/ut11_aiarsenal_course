# Тесты: ОбщийМодуль.ЦенообразованиеРасчет.РассчитатьЦену

- **Объект тестирования:** [src/CommonModules/ЦенообразованиеРасчет/Ext/Module.bsl](../../../src/CommonModules/ЦенообразованиеРасчет/Ext/Module.bsl), функция `РассчитатьЦену(Товар, Контрагент, Соглашение, ДатаРасчёта, Количество)`
- **Фреймворк:** xUnitFor1C
- **Тип тестов:** unit/edge — покрытие граничных условий и веток логики. Каркас `tests/` в проекте пока не создан, поэтому тест-кейсы описаны в формате псевдокода xUnitFor1C с явной подготовкой данных ИБ; при появлении каркаса переносятся в `*.bsl`-файлы тестов без изменения сценариев.
- **Сигнатура результата:** `Структура{Цена, ПроцентСкидки, ПримененныеСкидки[], Основание}`

## Особенности объекта, важные для тестирования

1. Функция активно обращается к серверным данным: регистр сведений `ЦеныНоменклатуры`, регистр накопления `Закупки`, справочник `Акции`, `ОбщегоНазначения.ЗначениеРеквизитаОбъекта`, `Константы.МаксимальнаяСкидкаПоУмолчанию`, `ПараметрыСеанса.КэшЦен`. Чистого unit-теста без подготовки данных ИБ (или без подмены зависимостей) не получится — тесты ниже описывают требуемые фикстуры явно.
2. Кэш цен хранится в `ПараметрыСеанса.КэшЦен` (см. `ПолучитьКэшЦен`/`ОбновитьКэшЦен`) — сквозной для сеанса побочный эффект, который может исказить результаты соседних тестов. Каждый тест обязан либо очищать `ПараметрыСеанса.КэшЦен = Неопределено` в `Подготовка()`, либо использовать уникальные Товар/ВидЦены/Дату, чтобы не попасть в чужой кэш.
3. Параметр `Количество` в теле функции не используется (см. карту модуля, п.7.3) — отдельный тест фиксирует это как текущее поведение, чтобы регресс был заметен, если логика изменится.
4. Проверка минимальной цены задублирована в `ПрименитьПравилаЦенообразования` и `ПроверитьОграничения` — тесты не различают, какая из веток сработала, а проверяют только итоговый контракт.
5. `ПроверитьОграничения` вызывается с жёстко зашитой `МаксимальнаяСкидка = 25`, значение `Константы.МаксимальнаяСкидкаПоУмолчанию` в этой функции не используется — см. TC-13.

## TC-01. Базовая цена не найдена (нет строки в регистре)

- **Подготовка:** Товар без записей в `РегистрСведений.ЦеныНоменклатуры` на дату расчёта. Кэш очищен.
- **Действие:** `РассчитатьЦену(Товар, Контрагент, Соглашение, ДатаРасчёта, 1)`
- **Ожидаемо:**
  - `Результат.Цена = 0`
  - `Результат.Основание = "Базовая цена не найдена"`
  - `Результат.ПроцентСкидки = 0`, `ПримененныеСкидки` — пустой массив
  - Функции скидок (`ПолучитьСкидкиКонтрагента` и далее) не должны влиять на результат — ранний выход до их вызова.

## TC-02. Цена найдена, но её период в будущем относительно ДатаРасчёта

- **Подготовка:** Запись цены с `Период > ДатаРасчёта`.
- **Действие:** расчёт на более раннюю дату.
- **Ожидаемо:** `ЦенаДействуетНаДату` = Ложь → `ПолучитьБазовуюЦену` = 0 → тот же контракт, что TC-01 (`Основание = "Базовая цена не найдена"`).

## TC-03. Цена найдена, но старше 365 дней от даты расчёта

- **Подготовка:** Запись цены с `Период = ДатаРасчёта - 366 дней`.
- **Действие:** расчёт на `ДатаРасчёта`.
- **Ожидаемо:** аналогично TC-01 — цена считается недействующей (`РазницаДней > 365`).
- **Граница:** отдельно проверить `РазницаДней = 365` (включительно) — цена должна считаться действующей (условие в коде строго `> 365`).

## TC-04. Соглашение не заполнено → вид цены "Основная"

- **Подготовка:** `Соглашение = Неопределено` (или пустая ссылка), есть цена по виду `Основная` на дату.
- **Действие:** `РассчитатьЦену(Товар, Контрагент, Неопределено, ДатаРасчёта, 1)`
- **Ожидаемо:** `ПолучитьВидЦеныПоСоглашению` вернула `Справочники.ВидыЦен.Основная`; расчёт продолжился на базовой цене этого вида.
- **Примечание:** при `Соглашение = Неопределено` дальнейшее обращение к `Соглашение.МинимальнаяЦена`/`.ПравилоОкругления`/`.Наименование` в `РассчитатьЦену` вызовет ошибку обращения к несуществующим полям неопределённого значения — зафиксировать как известное ограничение (см. раздел «Замечания» ниже), тест-кейс проверяет это как ожидаемое исключение, а не падение с непонятной причиной.

## TC-05. Соглашение заполнено, но реквизит ВидЦены не задан

- **Подготовка:** Соглашение с пустым `ВидЦены`.
- **Ожидаемо:** `ПолучитьВидЦеныПоСоглашению` возвращает `Основная` (fallback).

## TC-06. Без скидок (пустой список у контрагента)

- **Подготовка:** контрагент без акций/объёма/VIP/новизны/истории >12 мес.; базовая цена = 1000; соглашение без `МинимальнаяЦена` (0); `ПравилоОкругления` не задано (пусто/иное значение).
- **Ожидаемо:**
  - `ПримененныеСкидки` — пустой массив
  - `ПроцентСкидки = 0`
  - `Цена = 1000` (без изменений, без округления — ветка `Иначе` в `ОкруглитьЦену` возвращает цену как есть)
  - `Основание = "Расчёт по соглашению " + Соглашение.Наименование`

## TC-07. Одна скидка — VIP категория (+5%)

- **Подготовка:** `Контрагент.Категория = Перечисления.КатегорииКлиентов.VIP`, базовая цена 1000, без прочих скидок.
- **Ожидаемо:** `ПроцентСкидки = 5`, `Цена = 950`, в `ПримененныеСкидки` один элемент с `ТипСкидки = "VIP"`.

## TC-08. Комбинация всех источников скидок одновременно

- **Подготовка:** одновременно выполняются условия:
  - действует акция (общая, `Товар = ПустаяСсылка`) с процентом, например, 10;
  - объём закупок контрагента за 3 месяца ≥ 1 000 000 (скидка 7%);
  - категория контрагента `VIP` (5%);
  - обороты по регистру `Закупки` за 12 месяцев > 0 (скидка "Постоянный клиент" 3%).
- **Ожидаемо:**
  - `ПримененныеСкидки` содержит 4 элемента в порядке: Акция → Объём → VIP → Постоянный клиент (порядок добавления, см. карту модуля п.8 — порядок не влияет на цену, только на состав массива);
  - `ПроцентСкидки = 10+7+5+3 = 25`;
  - `Цена = БазоваяЦена * (1 - 25/100)`.

## TC-09. Сумма скидок ≥ 100% — цена уходит в ноль/отрицательную зону

- **Подготовка:** базовая цена 100; скидки в сумме дают, например, 120% (акция 100% + VIP 5% + др., либо подобранная комбинация из реально возможных значений). `Соглашение.МинимальнаяЦена = 0`.
- **Ожидаемо:**
  - В `ПрименитьПравилаЦенообразования` итоговая цена станет отрицательной (100 * (1-1.2) = -20), поднятие до минимума не сработает, т.к. `МинимальнаяЦена = 0` (условие `МинимальнаяЦена > 0` ложно).
  - В `ПроверитьОграничения` при `МаксимальнаяСкидка = 25 > 0` и `ИтоговаяЦена < 0` → возвращается 0.
  - **Итог:** `Результат.Цена = 0` после округления (для `ДоРубля`: `Цел(0+0.5)=0`).
  - Это ключевой edge-кейс — проверяет защиту от отрицательной цены.

## TC-10. Минимальная цена соглашения выше расчётной

- **Подготовка:** базовая цена 100, скидка 50% → расчётная 50; `Соглашение.МинимальнаяЦена = 80`.
- **Ожидаемо:** `Цена = 80` (поднятие сработает уже в `ПрименитьПравилаЦенообразования`, дублирующая проверка в `ПроверитьОграничения` не меняет результат).

## TC-11. Округление — ДоРубля

- **Подготовка:** `ПравилоОкругления = Перечисления.ПравилаОкругления.ДоРубля`, цена после скидок = 123.4 и отдельно 123.5 (граница округления).
- **Ожидаемо:** `Цел(123.4+0.5)=123`; `Цел(123.5+0.5)=124`.

## TC-12. Округление — До10

- **Подготовка:** `ПравилоОкругления = До10`, цена = 124, отдельно 125.
- **Ожидаемо:** `Цел((124+5)/10)*10 = 120`; `Цел((125+5)/10)*10 = 130`.

## TC-13. Округление — Психологическое99

- **Подготовка:** `ПравилоОкругления = Психологическое99`, цена = 1050.
- **Ожидаемо:** `Цел(1050/100)*100+99 = 1099`.
- **Смежная проверка (не про округление, но про ограничение скидки):** зафиксировать, что `ПроверитьОграничения` в `РассчитатьЦену` вызывается с константой `25`, а не с `Константы.МаксимальнаяСкидкаПоУмолчанию`. Если константа в ИБ настроена на другое значение (например, 40), это никак не влияет на `РассчитатьЦену` — только на `РассчитатьСкидку`/`ОграничитьМаксимальнуюСкидку`. Тест должен явно провалиться, если поведение когда-либо синхронизируют (сигнал регресса/умышленного изменения контракта).

## TC-14. Кэш цен — повторный вызов не должен идти в регистр

- **Подготовка:** Первый вызов `РассчитатьЦену` для Товар/ВидЦены/Дата — заполняет `ПараметрыСеанса.КэшЦен`. Перед вторым вызовом изменить цену в регистре `ЦеныНоменклатуры` на другое значение (не через кэш).
- **Действие:** второй вызов с теми же Товар/Соглашение(→ВидЦены)/Дата.
- **Ожидаемо:** возвращается цена из кэша (старое значение), а не новая из регистра — подтверждает, что `ПолучитьКэшЦен` перехватывает запрос раньше обращения к БД.
- **Очистка:** после теста обязательно сбросить `ПараметрыСеанса.КэшЦен = Неопределено`, иначе последующие тесты в сеансе получат неверные данные (см. общее замечание №2).

## TC-15. Параметр Количество игнорируется

- **Подготовка:** одинаковые Товар/Контрагент/Соглашение/ДатаРасчёта, два вызова с `Количество = 1` и `Количество = 1000`.
- **Ожидаемо:** результаты (`Цена`, `ПроцентСкидки`) идентичны — подтверждает текущее (возможно, ошибочное с точки зрения бизнес-логики) поведение: количество не участвует в расчёте цены за единицу. Тест фиксирует контракт "как есть"; при изменении поведения тест должен быть осознанно обновлён, а не просто исправлен на "красный→зелёный".

## TC-16. Ошибка записи истории расчёта не должна прерывать функцию

- **Подготовка:** сделать `РегистрыСведений.ИсторияРасчётаЦен.Записать()` невозможной (например, через блокировку записи или заведомо некорректные данные набора, если тестовое окружение это позволяет смоделировать), либо (если прямой сбой недоступен в тестовой среде) — тест помечается как требующий мока/подмены точки записи.
- **Ожидаемо:** `ЗаписатьИсториюРасчёта` перехватывает исключение (`Попытка/Исключение`) и пишет в журнал регистрации; `РассчитатьЦену` при этом успешно возвращает штатный `Результат` (не пробрасывает исключение наверх).
- **Статус:** ⚠️ Требует тестового окружения с возможностью инъекции сбоя записи регистра — в чистом xUnitFor1C без моков БД не воспроизводится напрямую; отметить как интеграционный, а не unit-тест.

## TC-17. Основание содержит наименование соглашения

- **Подготовка:** `Соглашение.Наименование = "Тестовое соглашение №1"`, базовая цена найдена.
- **Ожидаемо:** `Результат.Основание = "Расчёт по соглашению Тестовое соглашение №1"`.

## Замечания по тестируемости (для отдельного обсуждения, не блокирует написание тестов)

1. При `Соглашение = Неопределено` функция обратится к `Соглашение.МинимальнаяЦена` и упадёт с исключением до того, как дойдёт до `ПрименитьПравилаЦенообразования` — необходимо уточнить у разработчика, ожидаемое ли это поведение, или требуется явная проверка `ЗначениеЗаполнено(Соглашение)` в начале `РассчитатьЦену` (сейчас проверка есть только внутри `ПолучитьВидЦеныПоСоглашению`, но она не защищает остальные обращения к `Соглашение.*`).
2. Кэш в `ПараметрыСеанса.КэшЦен` делает функцию не чистой (impure) — при параллельном выполнении тестов в одном сеансе возможны конфликты. Рекомендуется либо генерировать уникальные тестовые товары на каждый тест, либо явно сбрасывать параметр сеанса в `Подготовка()`/`Завершение()` тестового класса.
